**需求状态机**（`app/requirements.py` `REQ_STATUSES`）：`draft` → 分析后无问题 `analyzed` / 有 must 级待确认 `pending_confirm` / 问题都答完 `confirmed` → 发起设计 `designing` → 人工标 `done` / `archived`。`designing / done / archived` 不会被 `_refresh_status` 回退。追加 / 重新解析 / 删除附件、重新提取或人工修改整理稿后分析结果不重置，但 `analysis_meta.inputs` 记录了分析时的附件指纹与整理稿版本，视图返回 `analysis_outdated`，分析页提示重新分析。

**任务状态机**（`app/tasks/store.py`）：`queued → running → completed / failed / awaiting_confirmation`。没有 `pending`、`done`。重启时 queued / running 一律标 failed。取消只对后台任务有效，前台同步任务返回 409；queued / running 却没有后台句柄的孤儿任务用 `cancel?force=true` 标记失败。已完成任务上的增量生成被取消 / 失败回到 completed（现有用例不动，新通过的点仍待生成），不进 failed。详情接口 `progress_detail`（job_active / modules_done / analysis_done / checkpoint_at）供页面判断在跑还是卡住。

## 1. 需求录入与解析

### 1.1 创建需求 `POST /api/v1/requirements`（`routes.py` `create_requirement`）

1. 从 `urls` 和原文里提取链接，去重，超过 10 条返回 400。
2. 权限 `requirement.edit`。项目不存在时管理员自动建项目，其他人 403。模块、版本必须属于该项目。
3. `source_type`：有文字且有文件或链接 `mixed`，只有文件 `file`，只有链接 `link`，否则 `manual`。
4. 入库：`req_id` 为 uuid 前 8 位，`status=draft`。原文为空但有文件或链接也放行。
5. 文件落盘到 `outputs/requirements/{req_id}/uploads/`，按 1MB 分块读，超过 `max_upload_size_mb=100` 的单个文件记为解析失败附件而不是整请求失败。
6. 文件走 `_schedule_attachment_parse`，链接走 `_schedule_link_fetch`，都是后台串行。创建时先沉淀一次原文到知识库。

`raw_text` 创建后没有任何接口能改；`PUT` 只能改标题、补充说明、版本、模块、状态。追加附件用 `POST /{id}/attachments`。删除仅系统管理员，有关联任务时需 `force`。

### 1.2 附件解析调度

- 附件字段：`parsing / parsed / error / text / chars / parsed_at`，链接附件多一个 `source_url`。
- `_parse_saved_attachment`：图片后缀走 `parse_image`（Vision），其余走 `parse_file` 再 `enrich_images` 回填内嵌图。所有异常都写进 `error`，不抛到外层。
- 服务重启时所有 `parsing=True` 的附件标失败，提示「重新解析」。
- 解析中禁止 AI 分析和发起设计（`_require_attachments_ready`，409）。解析失败的附件不阻塞，只在 `design_brief` 为空串时 analyze 返回 400。
- 重新解析 `POST /{id}/attachments/{att_id}/reparse`：任何已存文件都可以重解，不限于失败的。链接附件文件还在时只重解本地文件，不重新抓取。
- 解析完成后：`_schedule_requirement_ingest` 把原文和每个已解析附件各自沉淀为一篇 `requirement_docs`，再按确认快照沉淀分析。不触发项目画像提炼。
- 解析结果体检 `app/parsers/sanity.py`：文本 ≥ 1500 字且中文占比 < 5%，同时代码 / 样式类行 ≥ 30%，或乱码串 ≥ 5 处，或超过 50000 字，附件记 `warning`「疑似非需求文本」。AI 分析和发起设计遇到带告警的附件返回 409，页面弹窗确认后带 `ignore_warnings=true` 重试。

### 1.4 分片 `app/parsers/chunking.py`

`chunk_max_chars=20000`。按 `#` 标题切章节，贪心合并到不超限，单章超限按行切，小于 200 字的碎片并入相邻片。**片与片之间没有重叠**，跨片靠「全文模块大纲」补上下文。需求分析、拆解、直接生成、`/api/v1/parse` 预览都用它。附件解析本身不分片。

拆解与直接生成走 `requirement_chunks`（`app/agents/outline.py`）包一层：多需求合并的简报先按「【需求 i/n：标题】」切回各条需求再分片，**片不跨需求**，每片记住所属需求标题；整理稿末尾的「疑点 / 不一致清单」「疑似遗留草稿」不单独成片，带「只作参考、不要据此单独拆测试点」的说明挂到本需求最后一片末尾；章节装包剩下不到 1/8 阈值的小尾巴并入前片（略超 20000 字无妨；先 pop 再拼——曾写成 `parts[-2] = … parts.pop()`，三片时第一片被第二片覆盖、整段需求没拆）。整篇不超限时与原来一样只有一片。简报末尾的「【待确认事项的确认结论】」「【未确认的建议级事项】」两块不再整块落在最后一片：`split_qa_blocks` 先摘出来，`_attach_qa` 按每条「问（模块）：」所标模块对到哪一片的章节（`match_module`：模块名与章节模块名相同 › 章节名以「-模块名」结尾（模型给的不带文件夹名）› 模块名比章节更细归上一级 › 模块名是上级取其子节；对到的章节分散在几片、或没标模块的整体性问题放第一片），挂到那一片末尾，块头带「以下条目涉及本片章节，是人工确认过的正式规则，须拆成测试点并归入所标模块」——线上「连赢10/23」78 条确认结论（1.3 万字）原来全在只含增量奖池流水的第 4 片，那片的模型按「只拆本片内容」全跳过，ref 引用确认结论的测试点 0 条。「【人工补充说明】」是用户自己写的，不超过 2000 字时每片都带（`split_manual_note`），更长的只放第一片；从页面中间开始的片开头补一行「〔接上文〕所属章节：3 PC › 3.2 PC-活动详情页界面说明」（`_context_lines`，从段落中间切开的连本节标题一起给并标「续」），模型知道「#### 3.2.26 对应备注内容格式说明」在哪个页面下。

拆解与直接生成入口（`run_analysis` / `run_generation`，查漏 `gap_batches` 与经验延伸接口同样）先过 `clean_manual_sections`，两件事：**流程图代码块**（`flow_ascii` 画的分支树，含「──►」「→」的 ``` 块）围栏换成「【流程图：每条箭头是一步、分支标签是条件，每条分支的条件与结果都是正式规则，须逐条拆成测试点】…【流程图结束】」说明行，树的缩进保留、不含箭头的真代码块不动（线上 18 块流程图模型当示意图跳过，「活动流程总览」0 条自己的点）；整理稿里底稿核对 include 进来的「页面-人工收录」小节（线上 10 个小节模型 0 条测试点，夹着撤销按钮展示条件、导出文件名、下拉选项这类真规则）去掉样例行（数字 / 字母占比 ≥ 35%，`XXXX` 占位不算）、控件文案（「请输入 / 请选择」开头、不到 7 字且没有「：」）、分隔线与转录说明，剩下的规则以「**底稿核对时人工补入本页面的需求原句（正式需求，须一并拆解）：**」说明行代替标题留在所在页面末尾（大纲里不再出「人工收录」模块），清空的整节删掉；只动这些小节，存库的整理稿与任务 `context.requirement` 不变。

### 1.5 需求提取（AI 分析的前置节点，`app/agents/extraction.py`）

- 目的：原型导出包、整页截图的图片理解结果、多份文档拼在一起时，需求事实散落在导航 / 框架文字 / 样式脚本 / 重复页面之间，直接分析会被噪音稀释、分片后同一规则在不同片各写一遍。先把全部材料压成只含需求事实的整理稿，分析与测试设计以整理稿为准。
- 输入 `source_materials(item)`：原文 + 每个已解析附件 / 链接的文本（与早先直接送分析的材料相同），不含人工补充与待确认结论。
- 流水线 `run_requirement_extraction`：**结构分层** `structure_units` 按「【文件】 › 一 / 二级标题」切单元（同一文件相邻小单元打包到 20000 字，单元超限才按 1.4 再切并在路径加「第 k 段」，只有标题的空单元并入相邻单元；标题判定 `line_headings`：图片理解块里的「# 图片类型与整体说明」「# 图中文字原文」等节名与块内子标题不算章节（老材料没有结束标记时固定节名同样不算），文件自己的标题（文件头后、正文前的一级标题且下一个标题更低一级）不进路径，「页面：」前缀去掉，路径形如「连赢挑战.zip › PC / 活动入口」——之前图片块的一级标题把一页切成几十个假单元、同一页散进不同调用，模型只好自己起区块名、同一页在整理稿里出现两次）→ 各单元并行调 Prompt ### 1.6 下游用的需求文本 `design_brief`（`app/requirements.py`）

顺序拼接：`【需求整理稿】`（有基于当前材料的整理稿时，替代原文与附件文本；头部注明附件数与是否人工修改过）或 原文 → 每个附件 `【文件：名】` / `【链接：url】` + 文本 → `【人工补充说明】` → `【待确认事项的确认结论（以此为准）】`（confirmed 且有答案；有模块的写「问（模块）：…」） → `【未确认的建议级事项（按下列假设处理…）】`（open 且 suggest，无假设写「按行业惯例处理」，同样带模块） → `【AI 需求分析要点（已经人工过目）】`（当前分析的规则 / 边界 / 状态 / 权限四项文本，**带复核质疑 wrong / unsupported 且未处理的条目跳过**，与确认用的 `review_pending` 同一判定）。

AI 分析时传入 `analysis=None, questions=[]`，只用前三段，避免上一版结果自证。多需求合并设计时每段加 `【需求 i/n：标题】`，一次最多 20 条，必须同项目。

## 2. AI 需求分析闭环

### 2.1 `POST /requirements/{id}/analyze`

- 输入 `model`、`reviewer_model`（空则同分析模型）、`review`（空则取 `TIANGONG_ANALYSIS_REVIEW`，默认开）。
- 知识注入 `_analysis_knowledge`：`KnowledgeSteward.for_generation`，只查 `requirement_docs` 和 `business_rules`，预算 6000 字按 3:2 分（1500 / 1000，可互相让渡）。检索范围本项目 + 同业务线项目 + 公共层。**排除 `origin_ref` 为本需求 id 或本需求发起的任务 id 的文档**（本需求自己沉淀的原文 / 附件 / 已确认分析，以及派生任务沉淀的测试点 / 用例 / 终稿）。检索 query 为需求前 750 字加全部标题行。知识库为空直接跳过，任何异常降级为不注入。
- 项目画像通过 ContextVar 注入，预算 2500 字。
- 分析输入为 1.6 的 `design_brief`（传 `analysis=None, questions=[]`）：有整理稿时 quote 核验与独立复核对照的「原文」就是整理稿（整理稿本身已逐条对照过材料）。
- 流水线 `run_requirement_analysis`（`app/agents/analysis.py`）：
  1. `split_text` 分片；多片时先出全文大纲 `_outline_for`：需求是整理稿（带编号标题）时按标题生成不调模型（见 3.2），否则交模型（全文 ≤ 120000 字整篇送，否则每片取头部），`reasoning_effort=low`，失败不阻塞。
  2. 各片并行调 `requirement_analysis` Prompt，`reasoning_effort=high`，每片 Prompt 注明「第 i/N 片，quote 必须取自本片」并附大纲。任一片失败取消其余。
  3. `_merge_outputs`：10 项直接拼接，`open_questions` 按原文精确去重。
  4. `verify_analysis` 核验（见 2.2）。
  5. `review_analysis` 复核（见 2.3）。
- 11 个分析项：功能点、业务规则、前置条件、正常流程、异常流程、边界条件、状态变化、权限要求、外部依赖、风险点、待确认事项。前 10 项每条 `{text, quote}`，quote 要求逐字连续 20~80 字；规则 / 边界 / 状态 / 权限四项必须带 quote。`open_questions` 每条 `{question, level: must|suggest, reason, assumption, module}`，module 为问题所在章节的标题（「活动列表-基本配置」），整体性问题留空；模型没给的在核验阶段按问题文字里的章节号反查（`section_module`）。
- 写入 `analysis_meta = {id, model, chunks, by, at, knowledge, verification, review}`，上一版进 `analysis_history`（保留 10 版），`analysis_edits` 清空。待确认事项与旧问题按文本精确匹配合并：相同的保留旧状态和结论，AI 旧问题这次没出现的直接丢弃，人工问题全保留。

所有 `_chat_json` 调用在 system 末尾追加 `DATA_GUARD`，外部内容用 `wrap_data` 包成 `<<<数据:…>>>`；JSON 解析失败重试 1 次，输出被截断（`finish_reason=length`）不重试。

### 2.2 原文核验 `verify_analysis`

- `normalize`：NFKC 全角转半角 → 去掉所有非单词字符 → 小写。
- `quote_found`：规范化后不足 4 字返回 False；是原文子串返回 True；否则按中英文标点、换行、括号引号切段（**不按空格切**，保住「5 次」这类数字），只算 ≥3 字的段，命中字数占比 ≥ 0.7 为 True。
- 逐项：空文本和同项内规范化重复的条目丢弃；有 quote 的计入 `checked`，`verified=True/False`；无 quote 的 `verified=None`。
- 规则 / 边界 / 状态 / 权限四项 `verified` 不为 True 的**移出结果**，转成待确认事项 `{level: must, kind: unverified, key, text, quote, module}`，reason 区分「依据对不上」和「未给出依据」；module 由 `section_module(source, quote, text)` 定：整理稿按编号标题切节（标题链去重成「文件夹-页面-区块」），quote 整段命中的节，否则切段命中 ≥ 50% 的最像节（低于核验的 70%：只是定位不是证明），再没有按文字里的章节号找节，还没有按文字定位 `_section_by_text`（问题含某节叶子标题——去标点 ≥ 3 字且在整理稿里唯一，「日榜」「字段说明」这类不算 → 该节，标题更长、路径更深、正文重合更多依次优先；否则问题二字组合在各节正文的出现占比最高且 ≥ 20%、正文 ≥ 10 字 → 该节）。其他 6 项只打标不移除。
- 统计 `verification = {checked, verified, unverified, demoted}`。多片时 quote 对照的是全文。

### 2.3 独立复核 `review_analysis`

- 条件：复核开关开且原文 ≤ 60000 字；超限记 `review.skipped`，异常记 `review.error`，首轮结果保留。
- 输入：原文 + 核验后的条目清单（`n. text（依据：quote）`）+ 画像；不注入知识库。Prompt `requirement_analysis_review`，`reasoning_effort=high`，模型为 `reviewer_model or model`。
- 输出 `issues: [{key, n, verdict: wrong|unsupported, fix, note}]` 和 `missing: [{key, text, quote}]`。
- `apply_review`：issues 标到 `items[n-1].review`，不改原文；missing 先核验，四个证据项没通过的转待确认事项 `kind=review`（同样带 module），通过的以 `review.verdict=added` 追加；非证据项即使 quote 对不上也补入。
- `analysis.review = {model, wrong, unsupported, added, unverified_added}`。

### 2.4 人工拍板

- `POST .../analysis/items`，action：`add`（`manual=True`，可带 quote 并按原文核验）、`delete`、`edit`（去掉 review）、`accept_fix`（用 `review.fix` 替换，去掉 review）、`dismiss_review`（去掉 review，留痕记录驳回了什么意见）。五种都写 `analysis_edits`。
- `POST .../questions/{qid}/adopt`：核验降级或复核补充的问题一键加回对应项（`manual=True`，保留原 quote 并重新核验），问题置 confirmed。
- `_analysis_id = meta.id + "+{内容修改数}"`（只数 edit / delete / add），与确认快照的 id 不同即 `analysis_confirmed_stale`，所以改一条就要重新确认；`dismiss_review` 只留痕不算新版本。
- `_review_pending`：带 `review.verdict ∈ {wrong, unsupported}` 的条目数，`added` 不算。pending > 0 时单条确认、批量确认、加入评测集都不放行（单条 409，批量跳过），这些条目也不进 `design_brief`，发起测试设计可以继续但拆解上下文里没有它们。
- 待确认事项：`POST .../questions`（question、level、assumption、可选 module）人工补充，`POST .../questions/{qid}` 回答（answer 必填，`reopen=True` 只改回 open 不清答案），`PUT .../level` 调级别。每条带 `module`（所属页面 / 模块，表格「模块」列），盲区转入的另有 `ref`（出处原文）；`set_analysis` 合并时旧问题没模块、新分析定到了就补上；旧问题的匹配不再只认原文相同：`find_similar_question`（`question_similarity` = 规范化后字对 Dice 系数，规范化不足 10 字只认相同）≥ `QUESTION_SIM_AUTO`（0.6）且 `_same_numbers` 数字一致也算同一问题（模型重新分析常换说法），同一次分析一问两提只留一条。**跨需求沿用**：新问题先与 `_confirmed_question_pool`（同项目其他需求含回收站里的、status=confirmed 且有 answer 的问题，新需求在前）比，≥ 0.6 且数字一致 → 直接 `status=confirmed`，带 answer / by / at 与 `inherited={req_id, title, question, score}`，页面标「沿用「X」」；0.4（`QUESTION_SIM_HINT`）～0.6 或数字不同 → 只记 `suggested={req_id, title, question, score, answer, by}`，页面预填结论、标「历史结论参考」，人点确认才算。`answer_question`（确认或重新打开）都把 `inherited` / `suggested` 撤掉。**推荐答案**（Prompt `question_suggest`，`quality.run_question_suggest`，配置 `TIANGONG_QUESTION_SUGGEST` 默认开）：AI 分析完成后对全部未确认事项（must 与 suggest）按 ≤ 40 条一批并行调一次，原文 = `design_brief({**item, "analysis": None})`（整理稿 + 人工补充 + 已确认结论），历史结论 = `confirmed_question_pool`（同项目其他需求已确认的问题，问法相似 ≥ 0.3 的每条最多带 3 条），每条给 answer / basis（原文 › 历史结论 › 行业惯例）/ evidence / risk / confidence；basis=原文 的 evidence 用 `quote_found` 核验，对不上降为「行业惯例」并标 `unverified`；`set_question_suggestions` 写到事项 `suggested_answer`，页面与「历史结论参考」同一位置显示、同一预填框，人点确认才算；确认 / 采纳后撤掉，重新打开保留；故障只记日志。手动 `POST .../questions/suggest`（没有未确认事项 409）。**澄清记录**：每条事项带 `history=[{at, by, action, detail}]`，`_q_log` 在提出（AI 分析 / 核验降级 / 复核补充 / 人工补充 / 盲区转入）、沿用历史结论、AI 推荐答案、调整等级、确认（记采纳 AI 推荐 / 采纳历史结论 / 未采纳）、重新打开（带原结论）、采纳回分析、并入时追加；页面每条事项可展开「澄清记录 N 条」，顶部「澄清记录」切换按时间看全部事项的全程。阈值按线上校准：同一需求 88 条问题两两相似度最高 0.57，且那几对本就是一问两提。存量数据由启动时的 `backfill_question_modules` 回填（只处理没有 `module` 键的问题：有 quote 的按依据所在章节，问题末尾「（出处：…）」的按出处并补 `ref`，其余按章节号与文字（问题 + reason）；定不到的写空串并记 `module_v`，幂等；`_MODULE_BACKFILL_V`（现为 3）抬高后回填过的按新规则重算，模型 / 人工给的没有 `module_v` 不动）。`blocking_questions` = open 且 must，发起设计时有则 409。

### 2.5 确认与沉淀

- `confirm_analysis` 快照：`{by, at, analysis_id, analysis}`，analysis 为当前所有 list 项（不含 open_questions）。确认后后台 `ingest_requirement_entity`，有 `analysis_edits` 且 `TIANGONG_ANALYSIS_EVAL_AUTO_SAMPLE` 开时自动进评测集。
- 沉淀以**确认快照**为准：规则 / 边界 / 状态 / 权限进 `business_rules`，功能 / 前置 / 流程 / 依赖 / 风险进 `requirement_docs`，每个分析项一片，`origin=requirement, origin_ref=req_id`，同来源先删后写。取消确认即删除这两篇。
- 批量确认 `GET/POST /requirements/analysis/batch-confirm`：按项目（需 `requirement.edit`）或全部（管理员）把「未确认或已过期」的逐条确认并串行沉淀。`_batch_confirm_classify` 分四组：未分析、已确认当前版本、复核质疑未处理、待确认；只确认最后一组，前三组进 `skipped` 带原因返回，预览接口按组给数量。批量确认不自动加评测样本。
- 重新分析不会自动取消确认，知识库保留旧快照直到再次确认。

### 2.6 评测 `app/analysis_eval.py`

- 样本 id `req-{req_id}`，重复加入覆盖。`golden_from_analysis` 取各项文本，**排除仍带 wrong / unsupported 质疑的条目**，`added` 条目计入。标准答案可逐项修订。
- `POST /analysis-eval/runs`（管理员）：同时只能跑一个（409），可按项目或样本筛选，记录三个 Prompt 的当前版本号。后台串行，每样本设置画像上下文后重跑完整流水线（含知识注入与复核）。`predicted` 与标准答案同口径：复核判无依据的去掉、判理解错且给了改正的取改正文本（`predicted_after_review`，样本记录 `review_applied`）。
- `judge_sample`：同项内规范化相同的条目程序先配对，再调 `analysis_judge` 裁判（模型同 run.model，`high`），裁判漏报的预匹配会补回。
- `score_alignment` 只用裁判的 `matched` 和 `wrong`，编号对可带 AI 输出所在分析项（`[g, p, "boundaries"]`），归类不同的同一事实算匹配；未用到的 predicted 计 extra、golden 计 missing。指标：准确率 matched/(golden+extra)、捏造率 extra/predicted、理解错率 wrong/(matched+wrong)、遗漏率 missing/golden。按总计和按分析项汇总，分母为 0 记 None。
- 服务重启时仍 running 的评测标 failed。

## 3. 测试设计任务：需求拆解

### 3.1 创建与执行

- 入口：`POST /tasks`（上传或粘贴，`confirm_points` 默认 False、同步）与需求页 `POST /requirements/{id}/design`（默认 `confirm_points=True`、异步）。
- `context`：`requirement, confirm_points, model, reviewer_model, template_id, knowledge_space（空则同项目，指向别的项目需对方 knowledge.view）, project, requirement_id(s), requirement_title(s), module_id, version_id`，运行中追加 `resume_stage, generated_tp_ids, retried_at, retry_count`。
- 执行方式：进程内 `asyncio.create_task`，没有 Celery，`app/worker.py` 只是空骨架。同时执行的任务数由 `TIANGONG_TASK_MAX_CONCURRENCY`（默认 2）限制，超出的保持 `queued` 排队，排队中也可取消。单实例文件锁 `outputs/.instance.lock`，不支持多 worker。
- 持久化：`kv_docs` 一任务一行，写操作经单线程池先进先出。
- 检查点：拆解完成和每个模块生成完成时写 `checkpoint`，完成后清空。`resume_stage=confirmed` 在确认测试点时写入，之后失败只从已确认的点续跑。`retry` 分四种：补失败模块、确认后续跑、整体重跑、恢复已完成结果（failed 但已有 result.cases 且无检查点模块：只把状态恢复回 completed，不重跑）。`resume_stage=incremental` 在已完成任务做增量生成时写入。分片直接生成模式的检查点按片隔离：拆解结果存 `chunks[片号]`，模块结果键名加「片号:」前缀。

### 3.2 拆解 `analyze_requirement`（`app/agents/graph.py`）

- 分片规则同 1.4；多片时先出全文大纲，每片携带「第 i/n 片」、大纲（要求模块命名一致、本片没涉及的模块不生成、大纲只约束归属不限制测试点数量）、本片原文、画像、历史用例与缺陷知识。**不带前片摘要。**
- 大纲 `outline_from_brief`：需求是整理稿时按编号标题派生，粗细与模型无关——三级结构「## 文件夹 › ### 页面 › #### 区块」出「文件夹-页面-区块」（活动运营后台与商户管理后台的页面分得开；页面名已带文件夹名的如「PC」下的「PC-活动入口说明」不重复），两级「## 页面 › ### 区块」出「页面-区块」，正文 ≥ 150 字的区块单列，短区块与页面自身正文合成「页面」一个模块；〔疑似草稿〕区块、疑点清单、遗留草稿、没正文的空标题不进大纲；不足 3 个模块视为不是整理稿，回退模型大纲。多需求合并时模块名带「需求标题-」前缀，每片 Prompt 另注明「本片属于需求「X」，ref 写成「X › 页面或章节 › 需求点」」（两份整理稿章节号各自从 1 起，不带前缀分不清）。模块数直接决定生成阶段的调用次数（每个模块一次生成调用、都带整份需求），阈值 150 字是在 gpt-5.6-sol 自拟的 97 个模块与 gpt-6-sol 的 52 个之间取的。
- 颗粒度：Prompt `analyst` 要求一条测试点只验证一个结果，必填与格式、取值范围与默认值、不同角色 / 状态、成功与失败、不同异常原因一律分条，不许用「；」把两条规则合写；拆开之后不再写一条合起来复述（已有「≤ 90 天允许」「> 90 天不允许」就不再写「相差 90 天允许、超过不允许」），整理稿里原型字段表与需求文档正文重复的同一条规则只写一条。2026-10-22 实测同一分片同一提示词 gpt-6-sol 拆出的条数只有 gpt-5.6-sol 的一半（101–134 对 205–234），差在它把多条规则合成一条；大纲粗细只占 15–30%。
- Prompt `analyst`，`reasoning_effort=high`，输出 `{modules: [{module, points: [{point, dimension, ref}]}], blind_spots}`。`dimension` 限 10 个维度；`ref` 格式「页面或章节 › 需求点」，最长 120 字；禁止 UI 外观类测试点。
- 兼容：`normalize_points` 识别 `modules/test_points/items/children/测试点…` 等别名；`extract_json` 依次尝试代码块、第一个完整 `{}`、数组包装，再按特征逐个对象抢救。
- 空结果：非分片空则再试一次仍空报错；分片单片空跳过，全部空才报错。
- **经验延伸** `extend_points`（Prompt `point_extend`，`reasoning_effort=high`，配置 `TIANGONG_POINT_EXTENSION` 默认开；`run_analysis` / `run_generation` 的参数 `extend` 可覆盖）：明文拆完每片紧接着再调一次，输入本片原文 + 刚拆出的全部明文测试点（模块 / 描述 / 维度 / ref）+ 画像 + 历史用例与缺陷知识，按资深测试的经验清单（重复与并发、中断与恢复、跨天 / 结算时刻 / 改系统时间、空数据 / 超大量 / 并列排序 / 精度 / 特殊字符 / 存量兼容、前后台一致与被撤销后仍操作、越权 / 篡改 / 重放、范围外与枚举外、多端多币种多语言、资金多扣少发重复发与对账、回归影响）补需求**没写**但该测的场景，输出 `{extensions: [{module, point, dimension, ref, basis}]}`。只延伸不复述、不给需求没有的功能加需求；`basis` 一句话写为什么要测（历史缺陷优先）。程序兜底：module 必须是已有模块（同名 › 互相包含 › 名字相似 ≥ 0.5 挂最像的，否则跳过）、与已有点或本轮前面的延伸点 Jaccard ≥ 0.75 跳过、没 basis 跳过、总数截到明文点数的 1/3（至少 3 条，模型按风险排序所以截掉的是靠后的）。合格的以 `source=derived` 追加进对应模块（`apply_extensions`），实体化后 `status=pending` 与明文点一起审核；延伸故障只丢延伸、明文点照常，trace 记「经验延伸」一步。拆解和生成的职责分开：`analyst` 只认需求原文宁多勿漏，延伸只补需求之外、条数受限、每条带依据，混在一次调用里模型会把「需求里有」和「经验上该测」搅在一起。测试点页「经验延伸」按钮（`POST /tasks/{id}/points/extend`）对已有任务再跑一轮（给关掉自动延伸的任务补、或审完一轮后再要一轮），走 `add_points(source=derived)` 同样的相似度拦截。
- 延伸点到用例：`confirmable_points` / 增量生成投影 / 确认请求体三处都把 `basis` 带给生成 Agent；`generator` 规则 6 改成「明文点只依据需求、带 basis 的延伸点按描述与 basis 设计用例，不以需求未提及为由跳过」，remark 以「经验延伸：」开头写 basis，优先级默认 P2（资金多扣少发重复发 / 数据丢失 / 越权 P1，体验类 P3）；`reviewer` 不得以「超出需求」打回延伸用例，只评触发手段可操作、预期可验证；`point_compare` 对带 basis 的 AI 多出点按场景合理性判价值。前端：来源列紫色「延伸」、测试点下一行「依据：…」、工具栏计数「经验延伸 N」、脑图标签与依据节点、用例表 remark 以「经验延伸：」开头的标「延伸」、导出 xlsx 来源「经验延伸」并多一列「延伸依据」。
- 知识配额：`test_cases 5 / requirement_docs 3 / business_rules 2 / bug_history 2`，总预算 6000 字，拆解与评审注入用例库与缺陷库（2500 / 1000），生成与需求分析注入需求库与规则库（1500 / 1000）。复用提示 `_reuse_hints` 向量 top 5、相似度 ≥ 0.78、取 3 条。

### 3.3 拆解后质量检查（仅 `confirm_points=True` 路径）

`_run_point_quality_checks`，期间 `progress=quality_check`，此时确认返回 409。

- **盲区分片复核** `blind_spot_verify`：多片时每片对照全部盲区各调一次，任一片判「已说明」即剔除并记 `resolved_blind_spots`，单片失败盲区原样保留。
- **覆盖查漏** `gap_check`：长需求按章节分批（`gap_batches`，每批 ≤ `GAP_BATCH_CHARS=8000` 字，分片规则与拆解相同、确认结论跟到对应批、人工收录小节先清洗），每批只带与它章节相关的测试点——模块名对得上批里章节模块名的（`match_module`）跟那一批，对不上的按测试点 ref 里的章节号投票，都对不上的每批都带；对不上的点超过一半（模块名模型自拟、需求不是整理稿）或整篇不超一批时与原来一样整篇一次。各批并行，Prompt 要求逐句对照本批原文找没覆盖的规则（维度矩阵只是概览），coverage 按本批判断后合并（任一批未覆盖即未覆盖 › 有已覆盖即已覆盖 › 全不适用才不适用 › 其余待确认），additions 拼接，某批故障只丢该批。线上 7.6 万字 + 1255 条一次送（10.6 万 token）模型 9 秒回「全已覆盖、新增 0 条」，这一轮等于没跑。补点以 `source=gap, status=pending` 追加，与现有点 bigram Jaccard ≥ 0.75 的跳过；AI 来源的新增（查漏 / 补充 / 延伸）模块名先 `resolve_module` 归到已有模块（同名 › 互相包含取最短 › 相似 ≥ 0.6），人工新增不归位——从页面中间切开的批没有章节标题，模型会把模块写成裸名「新版操作记录」。矩阵合并后再 `apply_additions_to_coverage`：某维度有批判「未覆盖」但 additions 补了该维度的点，这轮结束就是「已覆盖」，补了 0 条才留「未覆盖」；每格说明 `coverage_notes`（「3/9 批判未覆盖，查漏补充 48 条」，故障批不算）存 `TaskRecord.coverage_notes`、前端格内显示。线上 9 批合并 7 个维度「未覆盖」而 303 条新增正是补它们的。
- **模块级组合延伸** `point_combine`（`run_point_combine`，配置 `TIANGONG_POINT_COMBINE` 默认开；查漏之后、查重之前，手动 `POST /tasks/{id}/points/combine`，body `modules` 只跑指定模块——页面按模块筛选后点）：每个未驳回测试点 ≥ `COMBINE_MIN_POINTS=3` 的模块各调一次（并发 `COMBINE_CONCURRENCY=6`，`reasoning_effort=high`），送该模块全部测试点（tp_id / point / dimension / ref / basis）+ 它所在章节的原文（`_module_texts` 复用 `gap_batches` 定位，对不上的用整篇），Prompt 按条件组合 / 流程串联 / 状态×角色×端 / 规则优先级 / 数据流转五种方法只在模块内找单条规则叠加后的交叉场景。程序兜底：模块固定为被处理的那个；`from` 只认本模块编号且 ≥ 2 条（只涉及一条的是单点不是组合，跳过）；没 basis 跳过；与本模块已有点 Jaccard ≥ 0.75 跳过；每模块 ≤ `COMBINE_MAX_PER_MODULE=8`；某模块故障只丢该模块，全部失败才抛。`add_points(source=combined)` 带 `combo_from`，待审核；摘要 `TaskRecord.point_combine`（一个模块都没送不覆盖）。页面来源列紫色「组合」、测试点下方「组合依据：…（由 TP012、TP015 组合）」，脑图节点与导出同步；延伸点的 basis 走同一条路进生成。
- **语义查重** `dup_judge`：两两 bigram Jaccard 为候选——同一页面内 ≥ 0.45，不同页面 ≥ 0.7（拆细后 20 来字的测试点重合率天然高，日榜 / 月榜 / 报名记录各自的字段与查询规则又本来相同，全放进去会出上千对）。页面按整组模块名的父子关系定（`module_pages`）：有子模块的自己就是页面（「后台-日榜排名」有「后台-日榜排名-字段说明」），否则归组里的父模块，都没有再去掉最后一段（`module_page`）——只看名字会把「后台-日榜排名」「后台-月榜排名」都当成页面「后台」。候选带两边模块名，按 `DUP_JUDGE_BATCH=40` 对一批并行送模型（一次塞上千对模型只判前一百多对），Prompt 明确「文字相同但页面 / 功能不同的是两个测试对象，判不重复」「同一模块里把已拆开的几条合起来复述、或只多一个边界值的合写判重复，删合写的那条」，每对都要有结论；某批故障只该批标「待复核」。判「不重复」的对不进列表，但两条去标点后同文却判不重复的留下来标「同文不同对象」（`SAME_TEXT_VERDICT`），人看到同一句话出现几遍时知道是有意保留、认可就忽略；存 `dup_report`。前端疑似重复列表两边各显示所属模块，「同文不同对象」橙色标签并在说明里给处置方式。
- **独立评审** `point_review`（`run_point_review`，配置 `TIANGONG_POINT_REVIEW` 默认开；查漏、查重之后，手动 `POST /tasks/{id}/points/ai-review`）：按 `gap_batches` 分批，每批送本批原文 + 本批待审核的测试点（带 ref / basis），Prompt 只挑七类硬伤（合写 / 不可验证 / 数值改写 / ref 对不上 / UI 外观 / 超出需求 / 维度不符），程序只收批内编号与枚举内判定、一条点一个意见，数值改写 / ref 对不上 / 超出需求的 quote 用 `quote_found` 对本批原文核验、对不上标 `unverified`，某批故障只丢该批。`apply_ai_review` 把意见标到 `p.ai_review={verdict, fix, note, quote, unverified?, at}`，这次没意见的清掉上次的；`apply_point_review` 通过 / 驳回 / 修改时撤掉；摘要存 `TaskRecord.point_review`。前端红字意见、「按建议修改」预填、筛「有 AI 评审意见」。
- **用例语义查重** `case_dup_judge`（`run_case_dup_judge`，用例页「重复检查」`POST /tasks/{id}/cases/dup-check`）：`case_duplicate_candidates`（标题 + 前置 + 步骤 + 预期 Jaccard ≥ 0.6）的候选按 40 对一批送裁判，每对带两条用例的模块 / 标题 / 前置 / 步骤 / point_ids，判重复（keep）/ 可合并（merged_title）/ 不重复；不重复不进列表、没判到待复核、一批故障全待复核；存 `dup_report.cases`，`dup_pair_entities(record, "cases")` 以用例编号为存活集，忽略 / 重开复用 `record_dup_pair_action(kind="cases")`（`POST /tasks/{id}/cases/dup-pairs/{key}`）。
- **拆解去重** `dedupe_module_points`（实体化之前，`analyze_requirement` 与分片合并后各一次）：同名模块并成一个，同一模块里去掉标点空白后同文的测试点只留一条（模型会把同一字段表的规则输出两遍）；不同模块同文不动。
- 推理型模型把输出预算全花在推理上、`finish_reason=length` 且一个字正文都没有时，`_chat_json` 原样重试一次（有正文被截断的仍不重试）。
- 直接生成模式不跑查漏和查重，质量评分里覆盖度为空。

## 4. 测试点审核

- 字段：`tp_id`（`TP001` 起，删除不复用，最大值存 `analysis.tp_seq`）、`status: pending|approved|rejected`、`locked`、`reject_types`（16 种）、`fix_request`、`fix_scope`（5 种，默认「当前项」）、`reject_count`、`source: ai|gap|supplement|ai_fix|manual|blind_spot|derived|combined`、`basis`（延伸 / 组合点为什么要测）、`combo_from`（组合点的来源编号）、`version`、`warnings`（过粗检测）。
- 导出：`GET /tasks/{id}/points/export?fmt=xlsx|xmind&scope=all|approved`——xlsx 带来源 / 状态 / 审核意见 / 覆盖用例 / 延伸依据列；xmind（`export_points_xmind`）与页面脑图同结构：需求 → 模块（条数）→ 测试点「编号 描述」（labels=维度 / 来源 / 状态）→ 需求来源、依据（组合点带来源编号）、驳回意见、AI 评审意见、覆盖用例各一个子节点，备注里再写一遍；空模块不出现。
- `POST /points/review` 整批原子：`approve` 锁定并记 `final` 版本；`reject` 原因和类型必填，驳回 2 次提示人工介入；`modify` 乐观锁、`version+1`、回 pending、记 `manual`；`delete` 进回收站，模块空则移除；`unlock` 回 pending。每次写 `point_review_log`，通过的点沉淀到 `business_rules`。
- AI 修正：`POST /points/fix` 只输入被驳回的点，产出 `pending_fix` 提案（越权改动丢弃），`POST /fix/confirm` 后生效，拆分编号 `TPxxx-NN`，改过的回 pending 记 `ai_fix`。
- 盲区处置：`open / question / point / explained / ignored`，动作 `to_question`（写回来源需求的待确认事项，任务须关联需求；问题文本带「（出处：…）」，module 由 `ref_to_module(ref, 需求标题)` 把出处去掉需求标题与章节号得到，没出处沿用盲区模块，ref 原样存）、`to_point`（默认模块取盲区的所属模块，没有则「需求盲区」，ref 预填出处）、`explain`（note 必填）、`ignore`、`reopen`。`bs_id` 为文本 sha1 前 8 位，重新拆解后处置记录仍有效。
- 盲区出处（`module` / `ref`）：拆解 Prompt 要求盲区以对象形态输出 `{text, module, ref}`，`_blind_spot_refs` 取出存 `analysis.blind_spot_refs`（分片合并、直接生成的 `_merge`、检查点都带）；流水线里盲区本身仍是文本。模型没给的，`locate_blind_spot` 按文字开头的章节号在整理稿编号标题里反查：ref = 需求标题 › 祖先链（「后台 › 3 商户管理后台 › 3.4 日榜排名 › 3.4.7 查询功能说明」），module = 拆解模块里名字含该页面 / 区块标题的那个；多需求合并时同一章节号按模块前缀选那份整理稿。列表上显示模块标签与「出处：…」。
- 疑似重复：`open / ignored / resolved`，一方删除自动 resolved。
- 测试点审核留痕 `point_review_log`（tp_id / action / by / at）：前端在已通过 / 已驳回状态下显示最近一次的审核人与时间；多人同时审核同一任务时，一次操作刷新后新出现的别人的锁定会单独提示，不会被当成本次操作锁的。
- 确认生成 `POST /tasks/{id}/confirm`：有任一 approved 则只取 approved，一个都没审过取全部非 rejected，rejected 永不进生成。任务 completed 后再通过的新点走增量生成并合并重编号。

## 5. 用例生成与评审（LangGraph）

- 图：有 `test_points` 直接进 `generate`，否则先 `analyze`；`generate → review → (通过或 ≥3 轮) END / 否则 fix → generate`。`MAX_REVIEW_ROUNDS=3`，`recursion_limit=40`。
- 调度：按模块各跑一个子图，所有模块 `asyncio.gather` 并行，**没有批大小和并发上限**；checkpoint 里完成的模块直接复用。合并按「模块+标题」去重，失败模块记 `failed_modules / unresolved`，全失败才抛错。
- generate：system 为 `generator` Prompt 加模板 `prompt_spec`；user 为需求原文、测试点（带 tp_id 和 ref）、需求与规则知识、画像、记忆、学习规则。打回后用 `fix_instruction` 只返回改动的用例和 `deleted`，`merge_fix` 合并，内容变化 `version+1`，`renumber_case_ids` 重编为 `TC-{模块}-001`。生成后按标题正则剔除 UI 检查类用例，0 条报错。
- review：先确定性检查（字段校验、模板优先级与自定义列枚举、编号唯一连续），再 `reviewer` Prompt（`high`，模型取 `reviewer_model`），输出 `{passed, issues, missing, suggestions}`，8 类阻断性缺陷，`suggestions` 不打回；第 2 轮起只复核上一轮问题。3 轮仍不过写 `unresolved` 强制出稿，校验失败的用例跳过。
- 用例字段：`case_id, module, title, priority(P0–P3), precondition, steps[{action, expected}], keywords, remark, extras`；系统字段 `uid, point_ids, source(ai|manual|import|copy|ai_fix), version`。
- 收尾 `_finalize_task`：分配 uid、`case_reviews` 初始 pending、记 `prompt_versions`、首版 `ai_original`、`files_dirty=True`（下载时才导出）。质量评分 `_quality_report` 仅参考：覆盖度、用例 bigram Jaccard ≥ 0.6 的疑似重复对（≥3 对为高）、待确认数、未解决评审问题、评审轮次。
- 人工评审 `POST /tasks/{id}/review` 整批原子：`submit`（草稿转 pending）、`approve`（锁定记 `final`）、`reject`（可按 8 个字段或步骤定位）、`modify`（乐观锁，**直接通过并锁定**）、`delete`、`unlock`。通过的用例沉淀到 `test_cases`。
- AI 改用例 `POST /cases/fix` → 提案 → `/fix/confirm`，超出定位范围的改动还原，改过的回 pending。
- 多轮修订 `POST /revise`：锁定用例不进上下文，历史指令作 history 注入。离线终稿 `POST /tasks/{id}/final`：按标题配对算采纳率（验收口径 ≥ 50%），沉淀到知识库。
- 导出：`files_dirty` 或指纹变化时重导，`scope=approved` 只导正式用例。用例中心只收 `approved`。回收站恢复回 pending 记 `manual`，永久删除仅管理员。
- 需求变更：`POST /tasks/{id}/requirement-diff` 对比旧需求文本与新文本，输出受影响测试点和用例；`apply` 对非删除类变更定点改用例并替换 `ctx.requirement`。**不回写需求中心的原文。**

## 6. 测试计划与执行（`app/plans.py`）

- 状态 `not_started / in_progress / done / archived`。删除仅管理员，有执行记录只能归档。
- 只能加入本项目已通过的用例，加入时做完整快照并引用 `entity_versions`。有执行记录的用例不能移出。
- 分配：执行人须为项目内正常的非 viewer 成员或管理员，带 `expected` 的乐观锁冲突不覆盖。
- 轮次：有未结束轮次不能新建，新建轮次把 not_started / done 的计划置 in_progress。结束轮次时本轮已执行数达到计划内用例数则计划置 done，否则保持 in_progress。
- 执行状态只有 `pass / fail / blocked / skipped`，本轮没记录即未执行。fail 和 blocked 必填备注，fail 必选分类（用例步骤有误 / 用例预期有误 / 系统缺陷 / 环境问题 / 测试数据问题 / 其他）。未分配的执行时自动认领；代执行仅 project_admin / test_lead，记 `on_behalf_of`。重测旧结果进 `history`，整批失败回滚。
- **AI 挑选用例**（Prompt `plan_case_select`，`quality.run_plan_case_select`）：计划页「AI 挑选」→ `POST /plans/{id}/select`（goal 冒烟 / 全量回归 / 变更影响回归 / 模块专项、budget 条数上限、change_summary、focus_modules、task_ids）。候选 = 本项目任务（或指定任务）里已通过、还没在计划内的正式用例，精简视图不带步骤（`task_id:uid` 为 key，case_id 跨任务可能重复），`plan_exec_index` 最近一次执行失败的标 `failed_recent`；变更影响回归且没填摘要时自动带各任务 `requirement_diff` 的 summary + 变更条目 + 受影响用例。按 `SELECT_BATCH=300` 条一批并行，模型用批内 id 挑、程序只认批内 id 一条一次；合并后按 P0 › P1 › P2 › P3 再按模型顺序排，超预算截掉靠后的（`truncated`）；冒烟目标每个有 P0 的模块至少 1 条 P0，模型漏的程序补（`by=program`）；某批故障只丢该批、全失败 502；没有候选 409。结果是草稿存 `plan.selection_draft`（目标 / 预算 / 摘要 / 候选数 / 选中 / 没选说明 / 覆盖说明），弹窗表格勾选后按任务分组调 `POST .../cases` 加入。
- **失败 AI 归因与缺陷单**（Prompt `exec_triage`，`quality.run_exec_triage`）：计划执行页行内「AI 归因」或工具栏「AI 归因（失败 N）」→ `POST /plans/{id}/runs/{rid}/triage`（body `item_ids` 空 = 本轮全部失败），每条一次调用并行：用例快照 + 执行说明 + 来源测试点（按 `point_ids` 取 tp_id / point / ref）+ 关联的失败截图理解结果（`_triage_screenshots`：该用例的 image 附件 ≤ 3 张，走 `understand_image_bytes` 配 `EXEC_SHOT_PROMPT`，单张失败跳过）+ 用例所在模块的需求章节（`_triage_context` 用 `_module_texts` 定位，定不到用整篇前 8000 字）。输出五类归因（用例问题·步骤有误 / 预期有误 / 前置缺失、系统缺陷、环境问题、数据问题、需求变更）+ `failed_step` + 置信度 + 依据，系统缺陷时起草缺陷单（标题 / 严重度 / 前置 / 步骤 / 预期 / 实际 / 影响）。程序兜底：category 枚举外按系统缺陷且置信度低（不丢）、sub 只在用例问题下认、failed_step 收到步数内、bug 只在系统缺陷时留；`suggested_reason` 映射到 FAIL_REASONS（步骤有误 / 前置缺失 → 用例步骤有误、预期有误 → 用例预期有误、数据问题 → 测试数据问题、需求变更 → 其他）。结果写在 `run.results[item].triage`，失败分类 `reason` 不动，人「采纳」（`POST .../results/{item}/triage/adopt`，可指定分类，轮次结束后 409）才改并记 `triage.adopted`——用例问题类随之进 `_exec_failure_samples` 学习语料；单条故障只丢该条，全部失败 502。前端记录下方紫字「AI 归因：系统缺陷（置信度高，第 2 步，看了 1 张截图）」+「采纳为「系统缺陷」」+「复制缺陷单」（`bugText` 生成文本贴到外部缺陷系统）。
- **测试报告**（Prompt `test_report`，`quality.run_test_report`）：计划执行页「生成报告」→ `POST /plans/{id}/runs/{rid}/report`（本轮没有执行记录 409；轮次没结束出阶段性报告 `interim`）。输入由 `_report_inputs` 组装：范围（计划 / 周期 / 需求标题 / 覆盖模块 / 来源文件）、程序统计的执行数据（总体 / 按模块 / 按优先级，含未执行；`report_tables` 排成表送模型）、失败与阻塞清单（用例编号 / 失败分类 / 执行说明 / `triage` 与缺陷单摘要 / 复测次数）、计划内用例所属任务的需求（`requirement_ids`）上未关闭的待确认事项（编号 Q1…）。输出结论（可发布 / 有条件发布 / 不可发布）+ `verdict_basis` + 摘要 + 风险（text / impact）+ 遗留（ref / kind / text）+ 建议（when must / later / text）+ markdown。程序兜底：结论枚举外按有条件发布；有 P0 失败且分类不在 `CASE_PROBLEM_REASONS` 必须不可发布、还有失败 / 阻塞 / 未执行不得可发布，校正记 `adjusted` 并写在 markdown 开头；open_items 的 ref 只认输入里的编号、kind 枚举外按事项；markdown 为空用字段拼、没有表格补程序统计表。结果存 `run.report`（重新生成覆盖），`GET .../report.md` 下载；前端「查看报告」弹窗渲染 + 复制 + 下载。
- 旧任务级执行记录启动时迁移到自动建的计划，任务上写 `exec_migrated_to`，旧接口返回 409。
- 报表 `app/reports.py` 纯统计：AI 一次通过率、平均评审轮数、终稿采纳率、执行通过率与失败分类、测试点与用例的采纳 / 修改 / 驳回率。

## 8. 模型层（`app/llm/`、`config/models.yaml`）

- 默认 `gpt-6-astra`，`max_retries=1`，月预算 1500 美元。降级链只拼主模型自己的 `fallbacks` 一层：astra → sol → luna；sol → luna → 5.4；luna → 5.4-nano。
- 温度完全由 yaml 决定（GPT-6 三档 1，5.4 系 0.3），代码不覆盖。`reasoning_effort` 只对配置了的模型传；代码中拆解、需求分析、复核、裁判、评审传 `high`，大纲传 `low`。
- 重试：每模型 `1 + max_retries` 次，只对连接 / 限流 / 5xx 重试，退避 `min(20, base·2^n)`（限流 base 3），鉴权与参数错直接换下一模型，全链失败抛 `AllModelsFailedError`。全局并发 4。
- Vision：所选模型不支持时改用清单里第一个支持的；当前五个模型都支持。
- 调用日志 `ai_calls`：用途、Prompt 版本、模型、项目、任务、需求、状态、`finish_reason`、尝试次数、耗时、token、输入输出预览（各 3000 字）。异步写入，保留 90 天，启动时和每 24 小时清理一次。费用按单价折算，管理员看全平台月用量与预算。

## 11. 设计边界与修复记录

以下是有意如此、不打算改的行为：

- 未确认或已过期的分析仍会进测试设计上下文。确认是沉淀知识库的门槛，不是设计的门槛；只有带复核质疑未处理的条目被 `design_brief` 跳过。
- 批量确认不触发自动加评测样本，存量需求的分析没有经过逐条人工过目。
- Axure 导出包里的 svg 切片一律不送 Vision，矢量控件逐个导出数量大且没有业务信息。
- 附件追加 / 重新解析 / 删除不会清掉已有分析，只标 `analysis_outdated` 提示重新分析；是否重跑由人决定。整理稿过期则不同：分析与设计前会自动重提，因为过期整理稿缺了新附件的内容。
- 需求提取只摘录不改写；模型若改写了，条目保留并标 ⚠ 交人核对，不自动删除。反方向同样不放过：材料每一句都要有去向，模型没判定的按原句兜底收进而不是静默丢弃，噪音由人在底稿页排除——宁可多收，不可漏收。提取结果不单独沉淀知识库（沉淀仍以原文、附件与确认后的分析为准）。
- 需求变更 `requirement-diff` 的 `apply` 只改任务上下文里的需求文本，不回写需求中心原文；原文以需求中心为准。
- 分片之间不重叠，跨片靠全文大纲衔接；拆解不带前片摘要。片不跨需求；疑点清单 / 遗留草稿只作参考不单独拆点。
