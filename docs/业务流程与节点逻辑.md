# 天工业务流程与各节点实际逻辑

基于 v2.1.2 代码逐行梳理，写的是**代码现在怎么跑**，不是设计稿。阈值、状态值、函数名都取自代码；文末附「已知缺口」列出实现与设计意图不一致的地方。路径相对仓库根目录，`routes.py` 指 `app/api/routes.py`。

## 0. 全景


**需求状态机**（`app/requirements.py` `REQ_STATUSES`）：`draft` → 分析后无问题 `analyzed` / 有 must 级待确认 `pending_confirm` / 问题都答完 `confirmed` → 发起设计 `designing` → 人工标 `done` / `archived`。`designing / done / archived` 不会被 `_refresh_status` 回退。追加 / 重新解析 / 删除附件后分析结果不重置，但 `analysis_meta.inputs` 记录了分析时的附件指纹，视图返回 `analysis_outdated`，分析页提示重新分析。

**任务状态机**（`app/tasks/store.py`）：`queued → running → completed / failed / awaiting_confirmation`。没有 `pending`、`done`。重启时 queued / running 一律标 failed。取消只对后台任务有效，前台同步任务返回 409。

## 1. 需求录入与解析

### 1.1 创建需求 `POST /api/v1/requirements`（`routes.py` `create_requirement`）

1. 从 `urls` 和原文里提取链接，去重，超过 10 条返回 400。
2. 权限 `requirement.edit`。项目不存在时管理员自动建项目，其他人 403。模块、版本必须属于该项目。
3. `source_type`：有文字且有文件或链接 `mixed`，只有文件 `file`，只有链接 `link`，否则 `manual`。
4. 入库：`req_id` 为 uuid 前 8 位，`status=draft`。原文为空但有文件或链接也放行。
5. 文件落盘到 `outputs/requirements/{req_id}/uploads/`，按 1MB 分块读，超过 `max_upload_size_mb=100` 的单个文件记为解析失败附件而不是整请求失败。
6. 文件走 `_schedule_attachment_parse`，链接走 `_schedule_link_fetch`，都是后台串行。创建时先沉淀一次原文到知识库。

`raw_text` 创建后没有任何接口能改；`PUT` 只能改标题、补充说明、版本、模块、状态。追加附件用 `POST /{id}/attachments`。删除仅系统管理员，有关联任务时需 `force`。

### 1.2 附件解析调度

- 附件字段：`parsing / parsed / error / text / chars / parsed_at`，链接附件多一个 `source_url`。
- `_parse_saved_attachment`：图片后缀走 `parse_image`（Vision），其余走 `parse_file` 再 `enrich_images` 回填内嵌图。所有异常都写进 `error`，不抛到外层。
- 服务重启时所有 `parsing=True` 的附件标失败，提示「重新解析」。
- 解析中禁止 AI 分析和发起设计（`_require_attachments_ready`，409）。解析失败的附件不阻塞，只在 `design_brief` 为空串时 analyze 返回 400。
- 重新解析 `POST /{id}/attachments/{att_id}/reparse`：任何已存文件都可以重解，不限于失败的。链接附件文件还在时只重解本地文件，不重新抓取。
- 解析完成后：`_schedule_requirement_ingest` 把原文和每个已解析附件各自沉淀为一篇 `requirement_docs`，再按确认快照沉淀分析。不触发项目画像提炼。
- 解析结果体检 `app/parsers/sanity.py`：文本 ≥ 1500 字且中文占比 < 5%，同时代码 / 样式类行 ≥ 30%，或乱码串 ≥ 5 处，或超过 50000 字，附件记 `warning`「疑似非需求文本」。AI 分析和发起设计遇到带告警的附件返回 409，页面弹窗确认后带 `ignore_warnings=true` 重试。

### 1.3 解析器（`app/parsers/`）

| 格式 | 实际逻辑 |
|---|---|
| 分发 `base.parse_file` | 按后缀映射；未登记后缀按 utf-8-sig / gb18030 当文本读，解码失败或含 `\x00` 报不支持。视频、字体、`.indd`、`.pst` 直接报「不参与解析」。 |
| zip 类安全检查 | docx / xlsx / pptx / xmind 等 OOXML：解压总量 > 300MB、总量 > 10MB 且压缩比 > 200、条目 > 20000 均拒绝。 |
| txt / md / json / yaml / sql 等 | `#` 标题分级，其余为段落。 |
| docx | 按正文顺序遍历段落与表格；标题样式 `heading N / 标题 N`；列表前加 `- `。段落和表格单元格里的 `a:blip` 图片都按位置提取，合并单元格按关系 id 去重；文本框、页眉页脚、VML 图不提取。表格文字统一放文末，合并单元格文本会重复。 |
| pdf（PyMuPDF） | 超过 300 页拒绝。正文字号取众数，大于 1.15 倍的视为标题，字号从大到小对应 1、2、3 级。图片按 xref 跨页去重，占位附在该页文本后送 Vision。没有文本层也没有可提取图片的页按 150 dpi 整页栅格化送 Vision（大图自动切块）；整份都没有文本层且超过 60 页才报错。 |
| pptx | 直接读 `slideN.xml`，每页首段作标题。png / jpg / webp / gif 直接送 Vision，emf / wmf / svg 经 LibreOffice 栅格化后送（没装则跳过），备注不提取。 |
| xlsx / csv | 每个工作表一节。首行 ≥3 个短单元格且 60% 以上行填充过半判为「数据型」，逐行输出 `列名：值`；否则「文档型」按行拼接。嵌入图片按锚点行插占位。 |
| 图片 | 16 种后缀，svg / emf / wmf 先经 LibreOffice 栅格化。最长边 > 2000 时切块：步长 1880、重叠 120、末块只取剩余，块数 > 16 才整体缩小。每块 4 路并发，Prompt 注明块序与行列，输出 `【大图第 i/n 块】` 拼接。任一块失败整张图失败。单块编码后 > 5MB 拒绝。 |
| 文档内嵌图 `enrich.py` | 短边 < 100px 或 < 3KB 当装饰图跳过（Pillow 解不开的仍送）。Prompt 用 Prompt 管理里的「图片理解」加一句上下文。4 路并发，单图失败只替换成失败说明。 |
| 链接 | 仅 http(s)，拒绝私网 / 回环地址，重定向后再校验。30 秒超时，100MB 上限。HTML 去 script / nav / footer 后转 Markdown，正文为空提示可能需登录。 |
| 压缩包 zip / tar / 7z / rar | 跳过 `__MACOSX`、点开头、`~$`、绝对路径、`..`。`.js .css .ts .vue .map` 等脚本样式只汇总数量不解析。嵌套包最深 2 层。子文档图片占位先算好映射再一次性重编号。rar 需服务器装 unrar。 |
| Axure 导出包 | 识别条件：存在 `data/document.js` 或 `resources/scripts/axure/`。按站点地图顺序逐页取 html 可见文字（按行去重）加 `data.js` 里的说明备注；播放器框架页、脚本、样式跳过。页面 `images/{页}/` 下短边 ≥ 400px 且 ≥ 20KB 的位图当作整幅设计稿 / 截图送 Vision（全包最多 30 张），按钮图标等切图碎片和 svg 切片跳过。 |
| eml / msg | 正文加元信息，附件递归走压缩包逻辑。 |
| doc / xls / ppt / wps / rtf 等老格式 | LibreOffice 转新格式后解析，180 秒超时，没装 soffice 给明确提示。 |

### 1.4 分片 `app/parsers/chunking.py`

`chunk_max_chars=20000`。按 `#` 标题切章节，贪心合并到不超限，单章超限按行切，小于 200 字的碎片并入相邻片。**片与片之间没有重叠**，跨片靠「全文模块大纲」补上下文。需求分析、拆解、直接生成、`/api/v1/parse` 预览都用它。附件解析本身不分片。

### 1.5 下游用的需求文本 `design_brief`（`app/requirements.py`）

顺序拼接：原文 → 每个附件 `【文件：名】` / `【链接：url】` + 文本 → `【人工补充说明】` → `【待确认事项的确认结论（以此为准）】`（confirmed 且有答案） → `【未确认的建议级事项（按下列假设处理…）】`（open 且 suggest，无假设写「按行业惯例处理」） → `【AI 需求分析要点（已经人工过目）】`（当前分析的规则 / 边界 / 状态 / 权限四项文本）。

AI 分析时传入 `analysis=None, questions=[]`，只用前三段，避免上一版结果自证。多需求合并设计时每段加 `【需求 i/n：标题】`，一次最多 20 条，必须同项目。

## 2. AI 需求分析闭环

### 2.1 `POST /requirements/{id}/analyze`

- 输入 `model`、`reviewer_model`（空则同分析模型）、`review`（空则取 `TIANGONG_ANALYSIS_REVIEW`，默认开）。
- 知识注入 `_analysis_knowledge`：`KnowledgeSteward.for_generation`，只查 `requirement_docs` 和 `business_rules`，预算 6000 字按 3:2 分（1500 / 1000，可互相让渡）。检索范围本项目 + 同业务线项目 + 公共层。**排除 `origin_ref` 为本需求 id 或本需求发起的任务 id 的文档**（本需求自己沉淀的原文 / 附件 / 已确认分析，以及派生任务沉淀的测试点 / 用例 / 终稿）。检索 query 为需求前 750 字加全部标题行。知识库为空直接跳过，任何异常降级为不注入。
- 项目画像通过 ContextVar 注入，预算 2500 字。
- 流水线 `run_requirement_analysis`（`app/agents/analysis.py`）：
  1. `split_text` 分片；多片时先出全文大纲 `_outline_for`（全文 ≤ 120000 字整篇送，否则每片取头部），`reasoning_effort=low`，失败不阻塞。
  2. 各片并行调 `requirement_analysis` Prompt，`reasoning_effort=high`，每片 Prompt 注明「第 i/N 片，quote 必须取自本片」并附大纲。任一片失败取消其余。
  3. `_merge_outputs`：10 项直接拼接，`open_questions` 按原文精确去重。
  4. `verify_analysis` 核验（见 2.2）。
  5. `review_analysis` 复核（见 2.3）。
- 11 个分析项：功能点、业务规则、前置条件、正常流程、异常流程、边界条件、状态变化、权限要求、外部依赖、风险点、待确认事项。前 10 项每条 `{text, quote}`，quote 要求逐字连续 20~80 字；规则 / 边界 / 状态 / 权限四项必须带 quote。`open_questions` 每条 `{question, level: must|suggest, reason, assumption}`。
- 写入 `analysis_meta = {id, model, chunks, by, at, knowledge, verification, review}`，上一版进 `analysis_history`（保留 10 版），`analysis_edits` 清空。待确认事项与旧问题按文本精确匹配合并：相同的保留旧状态和结论，AI 旧问题这次没出现的直接丢弃，人工问题全保留。

所有 `_chat_json` 调用在 system 末尾追加 `DATA_GUARD`，外部内容用 `wrap_data` 包成 `<<<数据:…>>>`；JSON 解析失败重试 1 次，输出被截断（`finish_reason=length`）不重试。

### 2.2 原文核验 `verify_analysis`

- `normalize`：NFKC 全角转半角 → 去掉所有非单词字符 → 小写。
- `quote_found`：规范化后不足 4 字返回 False；是原文子串返回 True；否则按中英文标点、换行、括号引号切段（**不按空格切**，保住「5 次」这类数字），只算 ≥3 字的段，命中字数占比 ≥ 0.7 为 True。
- 逐项：空文本和同项内规范化重复的条目丢弃；有 quote 的计入 `checked`，`verified=True/False`；无 quote 的 `verified=None`。
- 规则 / 边界 / 状态 / 权限四项 `verified` 不为 True 的**移出结果**，转成待确认事项 `{level: must, kind: unverified, key, text, quote}`，reason 区分「依据对不上」和「未给出依据」。其他 6 项只打标不移除。
- 统计 `verification = {checked, verified, unverified, demoted}`。多片时 quote 对照的是全文。

### 2.3 独立复核 `review_analysis`

- 条件：复核开关开且原文 ≤ 60000 字；超限记 `review.skipped`，异常记 `review.error`，首轮结果保留。
- 输入：原文 + 核验后的条目清单（`n. text（依据：quote）`）+ 画像；不注入知识库。Prompt `requirement_analysis_review`，`reasoning_effort=high`，模型为 `reviewer_model or model`。
- 输出 `issues: [{key, n, verdict: wrong|unsupported, fix, note}]` 和 `missing: [{key, text, quote}]`。
- `apply_review`：issues 标到 `items[n-1].review`，不改原文；missing 先核验，四个证据项没通过的转待确认事项 `kind=review`，通过的以 `review.verdict=added` 追加；非证据项即使 quote 对不上也补入。
- `analysis.review = {model, wrong, unsupported, added, unverified_added}`。

### 2.4 人工拍板

- `POST .../analysis/items`，action：`add`（`manual=True`，可带 quote 并按原文核验）、`delete`、`edit`（去掉 review）、`accept_fix`（用 `review.fix` 替换，去掉 review）、`dismiss_review`（去掉 review，留痕记录驳回了什么意见）。五种都写 `analysis_edits`。
- `POST .../questions/{qid}/adopt`：核验降级或复核补充的问题一键加回对应项（`manual=True`，保留原 quote 并重新核验），问题置 confirmed。
- `_analysis_id = meta.id + "+{内容修改数}"`（只数 edit / delete / add），与确认快照的 id 不同即 `analysis_confirmed_stale`，所以改一条就要重新确认；`dismiss_review` 只留痕不算新版本。
- `_review_pending`：带 `review.verdict ∈ {wrong, unsupported}` 的条目数，`added` 不算。单条确认和加入评测集在 pending > 0 时返回 409。
- 待确认事项：`POST .../questions/{qid}` 回答（answer 必填，`reopen=True` 只改回 open 不清答案），`PUT .../level` 调级别。`blocking_questions` = open 且 must，发起设计时有则 409。

### 2.5 确认与沉淀

- `confirm_analysis` 快照：`{by, at, analysis_id, analysis}`，analysis 为当前所有 list 项（不含 open_questions）。确认后后台 `ingest_requirement_entity`，有 `analysis_edits` 且 `TIANGONG_ANALYSIS_EVAL_AUTO_SAMPLE` 开时自动进评测集。
- 沉淀以**确认快照**为准：规则 / 边界 / 状态 / 权限进 `business_rules`，功能 / 前置 / 流程 / 依赖 / 风险进 `requirement_docs`，每个分析项一片，`origin=requirement, origin_ref=req_id`，同来源先删后写。取消确认即删除这两篇。
- 批量确认 `GET/POST /requirements/analysis/batch-confirm`：按项目（需 `requirement.edit`）或全部（管理员）把「未确认或已过期」的逐条确认并串行沉淀。
- 重新分析不会自动取消确认，知识库保留旧快照直到再次确认。

### 2.6 评测 `app/analysis_eval.py`

- 样本 id `req-{req_id}`，重复加入覆盖。`golden_from_analysis` 取各项文本，**排除仍带 wrong / unsupported 质疑的条目**，`added` 条目计入。标准答案可逐项修订。
- `POST /analysis-eval/runs`（管理员）：同时只能跑一个（409），可按项目或样本筛选，记录三个 Prompt 的当前版本号。后台串行，每样本设置画像上下文后重跑完整流水线（含知识注入与复核）。`predicted` 与标准答案同口径：复核判无依据的去掉、判理解错且给了改正的取改正文本（`predicted_after_review`，样本记录 `review_applied`）。
- `judge_sample`：同项内规范化相同的条目程序先配对，再调 `analysis_judge` 裁判（模型同 run.model，`high`），裁判漏报的预匹配会补回。
- `score_alignment` 只用裁判的 `matched` 和 `wrong`，编号对可带 AI 输出所在分析项（`[g, p, "boundaries"]`），归类不同的同一事实算匹配；未用到的 predicted 计 extra、golden 计 missing。指标：准确率 matched/(golden+extra)、捏造率 extra/predicted、理解错率 wrong/(matched+wrong)、遗漏率 missing/golden。按总计和按分析项汇总，分母为 0 记 None。
- 服务重启时仍 running 的评测标 failed。

## 3. 测试设计任务：需求拆解

### 3.1 创建与执行

- 入口：`POST /tasks`（上传或粘贴，`confirm_points` 默认 False、同步）与需求页 `POST /requirements/{id}/design`（默认 `confirm_points=True`、异步）。
- `context`：`requirement, confirm_points, model, reviewer_model, template_id, knowledge_space（空则同项目，指向别的项目需对方 knowledge.view）, project, requirement_id(s), requirement_title(s), module_id, version_id`，运行中追加 `resume_stage, generated_tp_ids, retried_at, retry_count`。
- 执行方式：进程内 `asyncio.create_task`，没有 Celery，`app/worker.py` 只是空骨架。同时执行的任务数由 `TIANGONG_TASK_MAX_CONCURRENCY`（默认 2）限制，超出的保持 `queued` 排队，排队中也可取消。单实例文件锁 `outputs/.instance.lock`，不支持多 worker。
- 持久化：`kv_docs` 一任务一行，写操作经单线程池先进先出。
- 检查点：拆解完成和每个模块生成完成时写 `checkpoint`，完成后清空。`resume_stage=confirmed` 在确认测试点时写入，之后失败只从已确认的点续跑。`retry` 分三种：补失败模块、确认后续跑、整体重跑。分片直接生成模式的检查点按片隔离：拆解结果存 `chunks[片号]`，模块结果键名加「片号:」前缀。

### 3.2 拆解 `analyze_requirement`（`app/agents/graph.py`）

- 分片规则同 1.4；多片时先出全文大纲，每片携带「第 i/n 片」、大纲（要求模块命名一致、本片没涉及的模块不生成）、本片原文、画像、历史用例与缺陷知识。**不带前片摘要。**
- Prompt `analyst`，`reasoning_effort=high`，输出 `{modules: [{module, points: [{point, dimension, ref}]}], blind_spots}`。`dimension` 限 10 个维度；`ref` 格式「页面或章节 › 需求点」，最长 120 字；禁止 UI 外观类测试点。
- 兼容：`normalize_points` 识别 `modules/test_points/items/children/测试点…` 等别名；`extract_json` 依次尝试代码块、第一个完整 `{}`、数组包装，再按特征逐个对象抢救。
- 空结果：非分片空则再试一次仍空报错；分片单片空跳过，全部空才报错。
- 知识配额：`test_cases 5 / requirement_docs 3 / business_rules 2 / bug_history 2`，总预算 6000 字，拆解与评审注入用例库与缺陷库（2500 / 1000），生成与需求分析注入需求库与规则库（1500 / 1000）。复用提示 `_reuse_hints` 向量 top 5、相似度 ≥ 0.78、取 3 条。

### 3.3 拆解后质量检查（仅 `confirm_points=True` 路径）

`_run_point_quality_checks`，期间 `progress=quality_check`，此时确认返回 409。

- **盲区分片复核** `blind_spot_verify`：多片时每片对照全部盲区各调一次，任一片判「已说明」即剔除并记 `resolved_blind_spots`，单片失败盲区原样保留。
- **覆盖查漏** `gap_check`：10 维度（正常流程、异常流程、输入校验、边界值、状态转换、权限、数据、重复操作、中断、网络）输出已覆盖 / 未覆盖 / 不适用 / 待确认，补点以 `source=gap, status=pending` 追加，与现有点 bigram Jaccard ≥ 0.75 的跳过。
- **语义查重** `dup_judge`：两两 bigram Jaccard ≥ 0.45 为候选，需求截前 2000 字送模型判「重复 / 不重复」，模型故障全标「待复核」，存 `dup_report`。
- 直接生成模式不跑查漏和查重，质量评分里覆盖度为空。

## 4. 测试点审核

- 字段：`tp_id`（`TP001` 起，删除不复用，最大值存 `analysis.tp_seq`）、`status: pending|approved|rejected`、`locked`、`reject_types`（16 种）、`fix_request`、`fix_scope`（5 种，默认「当前项」）、`reject_count`、`source: ai|gap|supplement|ai_fix|manual|blind_spot`、`version`、`warnings`（过粗检测）。
- `POST /points/review` 整批原子：`approve` 锁定并记 `final` 版本；`reject` 原因和类型必填，驳回 2 次提示人工介入；`modify` 乐观锁、`version+1`、回 pending、记 `manual`；`delete` 进回收站，模块空则移除；`unlock` 回 pending。每次写 `point_review_log`，通过的点沉淀到 `business_rules`。
- AI 修正：`POST /points/fix` 只输入被驳回的点，产出 `pending_fix` 提案（越权改动丢弃），`POST /fix/confirm` 后生效，拆分编号 `TPxxx-NN`，改过的回 pending 记 `ai_fix`。
- 盲区处置：`open / question / point / explained / ignored`，动作 `to_question`（写回来源需求的待确认事项，任务须关联需求）、`to_point`（默认模块「需求盲区」）、`explain`（note 必填）、`ignore`、`reopen`。`bs_id` 为文本 sha1 前 8 位，重新拆解后处置记录仍有效。
- 疑似重复：`open / ignored / resolved`，一方删除自动 resolved。
- 确认生成 `POST /tasks/{id}/confirm`：有任一 approved 则只取 approved，一个都没审过取全部非 rejected，rejected 永不进生成。任务 completed 后再通过的新点走增量生成并合并重编号。

## 5. 用例生成与评审（LangGraph）

- 图：有 `test_points` 直接进 `generate`，否则先 `analyze`；`generate → review → (通过或 ≥3 轮) END / 否则 fix → generate`。`MAX_REVIEW_ROUNDS=3`，`recursion_limit=40`。
- 调度：按模块各跑一个子图，所有模块 `asyncio.gather` 并行，**没有批大小和并发上限**；checkpoint 里完成的模块直接复用。合并按「模块+标题」去重，失败模块记 `failed_modules / unresolved`，全失败才抛错。
- generate：system 为 `generator` Prompt 加模板 `prompt_spec`；user 为需求原文、测试点（带 tp_id 和 ref）、需求与规则知识、画像、记忆、学习规则。打回后用 `fix_instruction` 只返回改动的用例和 `deleted`，`merge_fix` 合并，内容变化 `version+1`，`renumber_case_ids` 重编为 `TC-{模块}-001`。生成后按标题正则剔除 UI 检查类用例，0 条报错。
- review：先确定性检查（字段校验、模板优先级与自定义列枚举、编号唯一连续），再 `reviewer` Prompt（`high`，模型取 `reviewer_model`），输出 `{passed, issues, missing, suggestions}`，8 类阻断性缺陷，`suggestions` 不打回；第 2 轮起只复核上一轮问题。3 轮仍不过写 `unresolved` 强制出稿，校验失败的用例跳过。
- 用例字段：`case_id, module, title, priority(P0–P3), precondition, steps[{action, expected}], keywords, remark, extras`；系统字段 `uid, point_ids, source(ai|manual|import|copy|ai_fix), version`。
- 收尾 `_finalize_task`：分配 uid、`case_reviews` 初始 pending、记 `prompt_versions`、首版 `ai_original`、`files_dirty=True`（下载时才导出）。质量评分 `_quality_report` 仅参考：覆盖度、用例 bigram Jaccard ≥ 0.6 的疑似重复对（≥3 对为高）、待确认数、未解决评审问题、评审轮次。
- 人工评审 `POST /tasks/{id}/review` 整批原子：`submit`（草稿转 pending）、`approve`（锁定记 `final`）、`reject`（可按 8 个字段或步骤定位）、`modify`（乐观锁，**直接通过并锁定**）、`delete`、`unlock`。通过的用例沉淀到 `test_cases`。
- AI 改用例 `POST /cases/fix` → 提案 → `/fix/confirm`，超出定位范围的改动还原，改过的回 pending。
- 多轮修订 `POST /revise`：锁定用例不进上下文，历史指令作 history 注入。离线终稿 `POST /tasks/{id}/final`：按标题配对算采纳率（验收口径 ≥ 50%），沉淀到知识库。
- 导出：`files_dirty` 或指纹变化时重导，`scope=approved` 只导正式用例。用例中心只收 `approved`。回收站恢复回 pending 记 `manual`，永久删除仅管理员。
- 需求变更：`POST /tasks/{id}/requirement-diff` 对比旧需求文本与新文本，输出受影响测试点和用例；`apply` 对非删除类变更定点改用例并替换 `ctx.requirement`。**不回写需求中心的原文。**

## 6. 测试计划与执行（`app/plans.py`）

- 状态 `not_started / in_progress / done / archived`。删除仅管理员，有执行记录只能归档。
- 只能加入本项目已通过的用例，加入时做完整快照并引用 `entity_versions`。有执行记录的用例不能移出。
- 分配：执行人须为项目内正常的非 viewer 成员或管理员，带 `expected` 的乐观锁冲突不覆盖。
- 轮次：有未结束轮次不能新建，新建轮次把 not_started / done 的计划置 in_progress。结束轮次时本轮已执行数达到计划内用例数则计划置 done，否则保持 in_progress。
- 执行状态只有 `pass / fail / blocked / skipped`，本轮没记录即未执行。fail 和 blocked 必填备注，fail 必选分类（用例步骤有误 / 用例预期有误 / 系统缺陷 / 环境问题 / 测试数据问题 / 其他）。未分配的执行时自动认领；代执行仅 project_admin / test_lead，记 `on_behalf_of`。重测旧结果进 `history`，整批失败回滚。
- 旧任务级执行记录启动时迁移到自动建的计划，任务上写 `exec_migrated_to`，旧接口返回 409。
- 报表 `app/reports.py` 纯统计：AI 一次通过率、平均评审轮数、终稿采纳率、执行通过率与失败分类、测试点与用例的采纳 / 修改 / 驳回率。

## 7. 知识库、画像、记忆、规则

### 7.1 知识库 `app/knowledge/`

- 向量库 Qdrant 嵌入式（`data/knowledge/qdrant`），COSINE；embedding `text-embedding-3-large` 3072 维，批 32，并发 4，重试 1 次无降级；维度不一致启动报错需重建。
- 台账 `knowledge_docs`：`space`（项目名或 public）、`level: public|project|module`（**没有业务线层**，同业务线靠检索时并入兄弟项目实现）、`category: test_cases|requirement_docs|business_rules|bug_history`、`origin: manual|task|requirement`、`origin_ref`。公共层只有管理员能写。
- 切片 600 字，按标题切、贪心合并、无重叠，<50 字并入前片；用例、缺陷、测试点模块、分析项整条一片。同 space + category + source 先删后写。
- 检索 hybrid：向量取 top_k×3，BM25（中文二元组，K1=1.5，B=0.75）取 top_k×3，RRF（k=60）融合截 top_k，**无相似度阈值**。范围 = 本项目（含模块层）+ 同业务线未归档项目 + 公共层。
- 自动沉淀开关：全局 `TIANGONG_KNOWLEDGE_AUTO_INGEST`（默认开）且项目 `knowledge_auto`。沉淀物：任务需求原文、需求实体原文与附件、审核通过测试点（一模块一片进规则库）、评审通过用例、离线终稿、已确认分析。删除任务 / 需求时 `forget(origin_ref)` 清掉非 manual 文档，恢复时重沉淀。
- 存量回溯：按项目串行，逐任务 `reingest_task` 再逐需求沉淀，单条失败计数不中断，可重复执行。

### 7.2 项目画像 `app/knowledge/profile.py`

## 8. 模型层（`app/llm/`、`config/models.yaml`）

- 默认 `gpt-6-astra`，`max_retries=1`，月预算 1500 美元。降级链只拼主模型自己的 `fallbacks` 一层：astra → sol → luna；sol → luna → 5.4；luna → 5.4-nano。
- 温度完全由 yaml 决定（GPT-6 三档 1，5.4 系 0.3），代码不覆盖。`reasoning_effort` 只对配置了的模型传；代码中拆解、需求分析、复核、裁判、评审传 `high`，大纲传 `low`。
- 重试：每模型 `1 + max_retries` 次，只对连接 / 限流 / 5xx 重试，退避 `min(20, base·2^n)`（限流 base 3），鉴权与参数错直接换下一模型，全链失败抛 `AllModelsFailedError`。全局并发 4。
- Vision：所选模型不支持时改用清单里第一个支持的；当前五个模型都支持。
- 调用日志 `ai_calls`：用途、Prompt 版本、模型、项目、任务、需求、状态、`finish_reason`、尝试次数、耗时、token、输入输出预览（各 3000 字）。异步写入，保留 90 天，启动时和每 24 小时清理一次。费用按单价折算，管理员看全平台月用量与预算。

## 9. 权限、审计、版本、回收

- 系统角色 `admin / member`；项目角色 `project_admin / test_lead / tester / viewer`。会话 72 小时，同用户名加 IP 失败 5 次锁 15 分钟，支持 TOTP。归档项目拒绝一切写操作。
