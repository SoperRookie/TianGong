# 天工 v2.1.4 发布说明

- 版本：v2.1.4
- 发布日期：2026-10-16
- 标签：`v2.1.4`（dev 分支）
- 性质：修复需求提取「源文件有、整理稿没有」的四层原因，并把提取节点改成「分层提取 → 原文逐项对照 → 自动补漏 → 人工逐条审核 → 版本存档」；无新增系统依赖，无表结构变更，升级步骤与 v2.1.0 相同

## 问题

生产上三条连赢活动需求（Axure 原型包 + 截图）的整理稿对照源材料逐行核查：剔除外观描述后仍有 12% ～ 17% 的需求句子没进整理稿，⚠ 条目里九成以上是模型改写原句时截掉了句尾条件。原因有四层，按影响从大到小：

| 原因 | 证据 | 本版处理 |
|---|---|---|
| 默认模型换成 gpt-5.6-sol 后提取量只有旗舰的三分之一 | 同样 21k 字输入：gpt-6-astra 输出 35k 字、gpt-6-sol 31k 字、gpt-5.6-sol 11k ～ 17k 字；没有截断，是模型把逐字摘录做成了摘要 | 新增 `TIANGONG_REQUIREMENT_EXTRACT_MODEL` 单独钉住提取模型；提取页模型下拉显示当前默认是哪个 |
| Prompt 要求「必须完整句子、字段 / 枚举 / 示例不单独成条」，逼着模型改写 | 原型里的需求大量是括号与列表，模型重组成句子时丢掉「无对应数据时显示 0」「点击后向下展开」这类句尾规则；带规则的示例被当样例数据剔除；图片理解结果被当界面清单修剪过重 | Prompt 改回逐字为先：材料是什么形式就按什么形式成条，字段清单 / 枚举值整行保留、带规则的示例保留、空数据与异常状态的显示规则保留；只剔除导航框架、脚本样式、纯样例数据和只讲颜色 / 位置 / 样式 / 可见性的行；只有文字完全相同才算重复，PC 与移动端各自保留 |

| 分片切在图片理解结果中间，后面的片不知道属于哪个文件哪个页面 | 7 万字材料切 4 片，第 2、3 片开头是「### 极速百家乐U01」「### 顶部玩法项」，来源只能写「需求材料 › …」 | 每片带上开头所处的标题路径「文件 › 页面 › 章节」 |

## 提取节点改成五步

| 步 | 做法 |
|---|---|
| 分层提取 | 不再按 20000 字机械切片：先按「文件 › 页面 / 章节」切成单元，同一文件的小页面打包、超限页面才再切，每次调用都带所含页面的路径；模型先列出页面区块清单再按区块逐字摘录，模块名「页面-区块」直接来自材料 |
| 原文逐项对照 | 不变：每条用与分析相同的规则对照材料，没逐字找到的标 ⚠ |
| 自动补漏 | 程序逐行找出材料里还没进整理稿的需求句（剔除标题、占位、汉字不足 8 个、只讲颜色 / 位置 / 样式 / 可见性的行、纯样例数据），连同已有模块清单送回模型判「补进 / 跳过」；只认送过去的原句，模型自己编的不收；最多两轮，累计不到 300 字不补。补进的条目标〔补漏〕，页面显示需求句覆盖率（补漏前后） |
| 人工逐条审核 | 「需求提取」页按模块逐条列出，可筛「⚠ 待核对 / 补漏 / 已处理」；每条「核对通过 / 修改（改后重新核验）/ 删除」；⚠ 条目都处理过才能点「完成审核」，之后再改动会取消标记。整篇改写仍保留，但改写后逐条结构失效 |
| 版本存档 | 历史从 5 版加到 10 版；页面可选历史版本看与当前版的逐行差异（当前多出 / 历史多出），一键恢复为当前版（当前版进历史，恢复版换新 id）。重提、逐条改动、整篇改写、恢复都让已有分析标「基于旧输入」 |

新接口：`POST /requirements/{id}/extraction/items`（item_id / action: ok | edit | delete / text）、`POST .../extraction/review-done`、`GET .../extraction/history`、`GET .../extraction/history/{index}`、`POST .../extraction/restore`；新 Prompt「需求提取补漏」可版本化；审计规则 +3。

## 底稿双向核验：材料每一句都有去向

网页版 GPT 做的静态 DOM 底稿（逐控件导出、带编号、不丢）证明了一件事：丢不丢应该按「材料里的每一句去了哪」来算，而不是按整理稿有多少条。本版把这套口径做进提取节点：

| 环节 | 做法 |
|---|---|
| 底稿 | 只记**产品写的原文**：Axure 页面文字控件行（带控件编号 `[u1125]`，解析时写进文本，审核可按编号回原型查）、文档段落、说明备注，其余按「文件序号-行号」；来源路径「文件 › 页面」。同一句在母版 / 面板各状态 / 各页面反复出现只记一个单元（记次数与页面）。图片理解的结果是中间产物不进底稿，只有「图中文字原文」段单独记一栏（低优先级：不送补漏、不兜底、不拦审核，可手动收录） |
| 核算 | 每个单元三种去向：**收录**（整理稿里逐字有它：整行子串或切段命中 ≥ 90%，不足 90% 的多半是改写时截掉了句尾条件，不算）、**排除**（有原因与判定方：模型 / 程序 / 人工；程序只判三类——小标题、纯样例数据或代码、不足 8 个汉字的短标签）、**待处理** |
| 补漏 | 待处理单元不设字数门槛全部送模型，带编号与「整理稿已有其中 N%」提示，Prompt 要求每句必须出现在 add 或 skip 之一；add 按原句收（改了写法的按原句），skip 的原因记到底稿；最多两轮 |
| 兜底 | 轮次用完模型仍没判定的，按原句收进「页面-待归类」并标〔兜底〕——宁可多收交人排除，不静默丢 |
| 页面 | 「需求提取」页新增「兜底」筛选与「底稿核对」视图。要人看的只有两栏：**需复核**（模型排除的、≥ 8 个汉字且带数字 / 条件词的句子，看一眼后「收录」或「确认」）和**待处理**；程序按规则排除的三类按类折叠，模型排除的按原因折叠，收录、图中文字各一栏（图中文字按「页面 › 图片 N」分组，每句标明来自哪一页的第几张图）；每句带编号、出现次数与页面。统计行「底稿 N 句（去重）：收录 / 排除（程序 / 模型 / 人工）/ 需复核（未看）/ 待处理 / 图中文字」。删了条目对应句回到待处理，**待处理不为 0 或需复核没看完不能完成审核** |

接口：`GET /requirements/{id}/extraction/ledger`、`POST .../extraction/ledger`（uid / action: include | exclude | confirm / reason）；审计规则 +1；旧整理稿没有底稿，重新提取后生效。

针对一份外部一致性报告（用旧整理稿对照原始 Axure，列出 ≤0 写成 >0、75/25 写成 35/65、第一名写成第一次、设计约束与入口位置示例被当示例剔除、流程图半句被当片段排除等问题）再收三处：① 逐字核验的规范化原本把 ≤ ≥ < > = % 全当标点去掉，「≤0 正常结算」和「>0 正常结算」规范化后相同，⚠ 永远不亮——含数字 / 运算符 / 百分号的条目改为整句严格命中（保留运算符与百分号、全角转半角），不走分段 70% 放行；四份真实稿 1,118 条含数字条目零误报。② 模型以「片段 / 脱离上下文 / 不完整」为由排除的句子，不论有无数字都进「需复核」（流程图节点「覆盖基础奖金成本中」这类往往是规则的后半句）。③ 提取与补漏 Prompt 明确设计要求与布局约束（专属设计、动态光效、入口尺寸并存、Banner 预留空间）、入口位置示例、流程图判断节点与分支半句都是需求，不得当外观 / 示例 / 片段剔除（Prompt 管理里改过版本的要同步）。报告列的 11 组错写在本版三份后台稿（5.6-sol 旧链路、5.6-sol 新链路、6-sol 本地）里均不存在，对照的是更早版本的稿。流程图按控件坐标重排与「是 / 否」标签就近归属留到下一版。

## 按《Axure 需求提取流程》落地：带坐标提取、按坐标还原阅读顺序、机器自校验

`docs/Axure需求提取流程.md` 总结了一套能「用机器证明没有丢失」的提取办法，本版把它做进解析器与提取节点（`app/parsers/axure.py`）：

| 流程要求 | 平台做法 |
|---|---|
| 每个控件当最小单元、带坐标提取；子控件坐标相对父控件 | 解析 `files/<页面>/styles.css` 的 `#uNNN { left; top }`，沿父控件链累加成绝对坐标；控件索引（类型 / 坐标 / 隐藏态 / 图片 src）随附件存，底稿核对页每句挂〔单元格 / 流程框 / 段落 / 下拉框 …〕标签，鼠标悬停看坐标 |
| 按坐标还原阅读顺序（行 4px 容差，再按列） | 同一父控件下的子控件按 `(round(y/4), x)` 排序，先控件自己的文字再子控件——动态面板各状态、组合各自连续，不与页面其它内容穿插。后台包流程图原来按 DOM 顺序是「结余部分计入第二天 → 覆盖基础奖金成本中 → 当日奖池 → 是否有结余」，现在是「当日奖池 → 是否有结余 → 结余部分计入第二天 → 覆盖基础奖金成本中」，判断框、分支标签、下一步相邻 |
| 表单控件文字不在 `_text` 里，必须单独抓 | 下拉框全部选项记「下拉选项：全部 / 日榜 / 月榜」，输入框 / 文本域的值与占位提示记「输入值：…」「占位提示：…」（checkbox / radio 的噪音值不记）。后台包因此多出 78 行枚举值与默认值，之前整页丢 |
| 隐藏态照样提取并标记 | `display:none / visibility:hidden`（含祖先）的控件照常进材料，索引标 `hidden`，底稿页显示〔… · 隐藏态〕；两个包分别 378 / 348 个隐藏控件（弹窗、面板另一状态），文字与可见态重复的按整块去重 |
| 第一级校验：整页字符多重集 vs 提取结果，与控件解析相互独立，必须 0 缺失 | 每页去掉 script / style / title / 注释后 `get_text` 的非空白字符计数，减去去重前全部控件行的字符计数；差集非空即报缺字（附件列表「自校验 ⚠ 缺 N 字」、底稿页顶部按包列出），并列出不在任何文字控件里的文本节点样例便于定位；差集为空显示「自校验 ✓ 0 缺字（N 页）」。两个真实包 18 页全部 0 缺字；自校验自己出错也落到结果里，不当「没问题」 |
| 需求语句逐字保留，疑点单列 | 提取 Prompt 新增 `doubt` 字段：错别字、PC 与移动（前台与后台）口径不一致、占位符、数值前后矛盾的条目原句照抄，疑点另写一句；整理稿该条标〔疑点：…〕，末尾自动生成「疑点 / 不一致清单」一节（供需求澄清与用例设计）；页面「疑点」筛选 |
| 终验编号归一化（原文「1、」整理稿「1.」或去掉序号不算丢） | 底稿收录判定去掉行首「1、」「注：1、」「三、」「①」「1️⃣」再比一次 |
| 附录由脚本生成逐控件原文、HTML 逐行包含校验、图片人工查看 | 对应已有的底稿（逐单元去向）、`verify_modules`（整理稿每条逐字回查材料）、底稿「图中文字」栏 |

新旧解析器对两个包逐行比对：行集合完全一致（前端 903 行、后台 1,705 → 1,783 行，多出的全是表单控件行），只是顺序变了。解析文本里控件行仍是「[u1125] 原文」，底稿 / 补漏 / 核验的编号口径不变；旧需求点「重新解析」即可得到新顺序与表单行，之后整理稿标过期、分析时自动重提。

|---|---|---|---|---|---|---|---|---|---|
| 后台 | 1,072 句（去重前 1,693） | 725 | 347（258 / 89） | 22 | 0 | 272 句（收录 125） | +110 / 13 | 33,707 字 101 模块 915 条，⚠ 0 | 281 秒 |

## 对照《连赢挑战赛_需求提取》复盘：表格行、逐字去重、短标签交模型

领导按《Axure 需求提取流程》对前端包手工提取了一份（`docs/xq/连赢挑战赛_需求提取.md`，490 条非示例行），与平台对需求「oks」的整理稿（566 行，gpt-6-sol）逐行比对：平台 566 行全部能在对方稿里找到（471 行逐字一致、70 行子串 / 超串、15 行命中「仅图片文案」，其余是图片 OCR 误读与底图噪声）；反过来平台缺 10 条有实质意义的内容，另有约 75 条标题 / 表头与 8 条更新记录是有意剔除的。10 条逐一回底稿查去向，根因在三处，都改了：

| 遗漏 | 根因 | 改法 |
|---|---|---|
| 连赢判断表「输赢金额=0 / <0」两行、流程图「该用户当局输赢金额是否=0」 | 底稿去重用去标点的 `normalize` 当键，「=0」「<0」被并进「>0」同一单元，而「>0」已收录，整个单元算收录（「（今日）」同样并进「今日」）；收录判定也用它，「=0」能靠「>0」过关 | 去重键改为逐字（只去空白，运算符 / 括号 / 数字都算字）；带数字 / 运算符的单元按 `strict_normalize` 严格比（与 `verify_modules` 同口径，函数搬到 `ledger.py` 共用） |
| 「连赢-奖励 / 连赢-报名退还 / 连赢-报名」「改为直接报名」「连赢数增加」「点击收起」 | 程序把 1～7 个汉字无标点无数字的行一律判「短标签」排除，不送模型 | 程序排除去掉短标签这一类（只剩小标题、纯样例两类）；按钮名 / 表头 / 字段名 / 交易类型名 / 状态与进度文案送补漏模型，Prompt 明确这些是用例要核对的界面文案要 add，只有区域名 / 装饰性控件名才 skip |
| 「表格失去列含义」「不变 / 清零的触发条件丢」 | Axure 表格每个单元格是一个控件，各自成行后「输赢金额=0」与「当前连赢次数“不变”」分家，模型各摘一条 | 解析器把同一行（top 相同）的单元格并成「输赢金额=0 ｜ 当前连赢次数“不变”」一条（表头行也是一行，编号取第一格，索引 `cls=table_row`，字符自校验不计分隔符）；提取 Prompt 要求整行连同「｜」照抄；底稿按单元格切段核算（「3局 ｜ +1分」拆成两条也算收录） |
| 「UTC+8 9.21 00:00:00～23:59:59」时区时间格式示例、「6/10」 | 没有汉字且不足 3 个英文单词一律判纯样例 | 带区间 / 比较符（～ ≥ ≤ < > = %）的不再由程序判样例，交模型；纯数字的「6/10」仍是样例 |

### 整理稿改成与《连赢挑战赛_需求提取》同样的层级

整理稿正文与页面不再是「模块 › 条目」两层平铺，改成 `extraction_outline` 算出的层级（`app/agents/extraction.py`）：

- 文头：`# 「需求标题」需求整理稿` + 来源（附件与页面清单）+ 提取原则 + 校验（逐字回查、底稿去向、原型自校验）；底稿核算跳过文头。
- `## N. 页面 〔来源：文件 › 页面〕`：按模块主来源分组，只在图片里出现的文案（来源「图片:N」）归最后一节「仅出现在图片中的文案」，每条标明来自哪张图。
- `### N.M 区块`：模块名去掉「页面-」前缀。
- 条目层级：连续的表格行（「A ｜ B ｜ C」，列数相同）还原成 Markdown 表格，表头是第一行，标记写在单元格里；以冒号结尾的短句（≤ 30 字）加粗成子标题；「1、」「①」「注：」「示例」开头且上一条是普通条目 / 子标题 / 表格的子项缩进一级；疑点清单作为最后一节编号。
- 页面「需求提取」默认进「预览」：整理稿正文按文档预览格式渲染（标题层级、表格、多级列表、加粗子标题，〔补漏〕〔疑点〕等标记弱化、⚠ 高亮；渲染器 `mdDoc`，不引外部库），与 `docs/xq/连赢挑战赛_需求提取.md` 在 IDE 里预览是同一个样子；整篇改写过的老整理稿也按预览显示。核对 / 修改 / 删除切到「逐条审核」页签，按接口返回的 `extraction.outline`（条目按 id 引用）渲染：页面 › 区块标题、表格（表头与数据行各带修改 / 删除）、加粗子标题、缩进子项；筛选时表头照留；条目来源与区块主来源相同的不重复标注。没有逐条结构的老整理稿按 Markdown 标题加粗显示。
- 底稿核算兼容新格式：表格行整行与每个单元格都算条目、加粗子标题算条目、孤行表格的单元格也算；逐条审核 / 底稿收录改动后按层级重生成正文并刷新文头统计。

### 对照后台包复盘：遗留草稿识别、整稿交叉核对、逐字去重

领导同样方法手工提取后台包（933 条非示例行）与平台对「oks2」的整理稿（1,590 条，含表格单元格）比对：平台 98.8% 在对方稿里有对应，19 条平台独有全是底图截图里现有系统的字段名；对方有而平台没有的 107 条里约 96 条是章节标题（平台用页面 › 区块编号替代），实质只差版本记录前 3 行。真正的差距是**结构判断**：原型画布上作者没删的两块旧版本（「连赢活动记录」页右侧的日榜 / 月榜 / 年榜三页签版本、「报名记录」页底部残留的旧版增量奖池流水）被平台当成正式需求收录成九个小节，拿去写用例会多出一整套「年榜」和一种不存在的「基础奖金」流水类型。本版四处改动：

| 问题 | 根因 | 改法 |
|---|---|---|
| 遗留草稿当正式需求 | 解析器按坐标排阅读顺序，画布远处的旧版本与主体按 y 穿插在一起，模型看不出它是另一块 | 解析器对每页控件做单链接聚类（横纵都相距 ≥ 1000px 才断开）：最靠左上的簇是主体，其余 ≥ 3 个控件的簇是「独立区域」，主体先输出、区域各自成块、前面一行 `【独立区域 N：主体右侧 2394px，108 控件，疑似遗留草稿】`，控件索引记 `region`，底稿页标「独立区域 N」。两个真实包：后台包正好识别出那两块（右侧 108 控件、下方 45 控件），前端包 0 块、其它页面无误判。提取与补漏 Prompt：这块照样逐字摘录，但与正式内容重复却有出入或用了别处没有的概念的，条目加 `draft: true`，第一条 doubt 写「疑似遗留草稿：…」；整理稿标〔疑似草稿〕、整块都是的区块标题标〔疑似遗留草稿〕并在末尾列「疑似遗留草稿」一节；页面有「疑似草稿」筛选与红标 |
| 跨页面 / 跨文档矛盾抓不到（版本记录写「取消第一名机制」正文仍是旧规则、盈利报名退款口径前后台不一致） | 提取按页面分片，单页看不见别的页 | 新增最后一步**整稿交叉核对**（Prompt `requirement_extract_crosscheck`，一次调用，输入全部条目带 id，≤ 15 万字）：只找跨页面矛盾与疑似遗留草稿，`doubts` 按 id 追加到条目疑点、`drafts` 按模块名整块标草稿；模型出错或关闭（`TIANGONG_REQUIREMENT_EXTRACT_CROSSCHECK=false`）只跳过，不影响提取 |
| 版本记录前 3 行丢 | 模型把更新记录表当样例跳过，只留了带规则的第 4、5 行 | 提取与补漏 Prompt 明确：版本记录 / 更新记录表整表保留（表头和每一行整行照抄），更新说明就是需求变更线索 |
| 自报「待处理 14」但兜底了 16 条 | `_merge_modules` 用去标点的 normalize 去重，兜底收进来的「输赢金额=0」被已有的「输赢金额>0」并掉，单元仍是待处理 | 合并去重与条目 id 都改成逐字键（只去空白） |
| 底图截图里现有系统的字段名混进来 | 图片理解把旧界面的表单字段、列名、按钮名都转录了 | 提取 Prompt：后台原型里贴的现有系统页面截图只是定位参考，说明文字没提到的字段名 / 列名 / 按钮名不摘 |

### 流程图还原：流程框 + 连接线 → 「A —是→ B」

原型里的流程图是流程框加连接线，逐框提文字只剩一堆孤立的框（「用户单局投注」「当前连赢记录清零」…），连线关系全丢，整理稿里看不出流程。解析器现在读连接线的线段定位（`#uNNN_seg0` 是线、小方块是箭头，`styles.css` 规则正则放宽到线段），从原点沿线段走到头得到起止点，箭头贴在哪头哪头是终点，端点落在哪个带文字的控件框内（外扩 10px）就连到它，连接线自己的文字（是 / 否 / Y / N）作分支标签；按连通分量分成几张图，从起点（没有入边的框）深度优先列边，每张图包在 `【流程图 N：K 个节点 M 条连线】…【流程图结束】` 里插在最后一个节点后面。两个真实包的需求说明页各还原出 4 张图（活动流程总览、连赢判断、奖池统计、机器人占位）。流程块是派生内容：底稿与需求句覆盖率不记块内行（各框文字另有原行，靠流程行命中），自校验不受影响。提取 / 补漏 Prompt 要求流程行一行一条照抄（箭头与分支标签不改）；整理稿里连续的流程行成稿为代码块，预览里就是文档里那种文字流程图，逐条审核里等宽字体成块。

### 对照文档再收：页面顺序、疑似草稿只认画布位置、正文现算

- 页面顺序改成与手工稿一致：版本 / 更新记录最前，需求说明（背景、总体规则）其次，各功能页面按材料顺序，只在图片里的文案最后；模型把来源写成「图片10」「图片 7」的也归图片文案节。
- 疑似草稿只认独立区域：提取模型与交叉核对模型在别处标的草稿一律去掉（前端包 `需求说明-活动规则说明`、后台包 9 个模块都是误报），`island_keys` 从材料里取独立区域内的句子，模块半数以上条目来自那里才能标草稿。
- 修一个底稿核算 bug：没有文头的正文（补漏 / 兜底阶段核算用的）被当成有文头切掉了第一节，兜底收进第一节的句子仍算待处理（前端包自报「待处理 36」就是它），现在只有以 `# ` 开头的文头才切。
- 看「ok3」的提取结果再收三处：流程框的文字与分支标签不再和流程行重复成条（模型常把框文字也逐条抄一遍，`dedupe_flow_nodes` 去掉，底稿按流程行照样对回）；小标题（「参与方式：」「报名规则说明」）不再由程序排除，提取与补漏 Prompt 要求当条目收，整理稿排成子标题给下面的条目当上下文（程序排除只剩无汉字的纯样例一类）；交叉核对疑点里引用的条目 id 换成模块名。这些收口（含疑似草稿只认独立区域）在成稿与详情接口里都按当前规则执行，老整理稿不用重新提取。
- 需求详情接口里的整理稿正文按当前成稿规则现算：页面顺序、表格、流程块、文头随代码升级即时生效，老需求不用重新提取。
