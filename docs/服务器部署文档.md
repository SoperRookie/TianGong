# 天工 服务器部署文档

适用版本：v1.0.3。本文覆盖两种部署方式，任选其一：

- **方式一：Docker 部署**（推荐）。`docker compose` 拉起 MySQL、应用、Nginx 三个容器，一条命令启动，升级只重建应用镜像。
- **方式二：裸机部署**。Python 虚拟环境 + systemd 托管 + 宿主机 Nginx，适合已有 MySQL 与运维规范的环境。

两种方式的环境变量、数据目录、迁移与运维事项相同：先看第 1、2 节的公共部分，再按所选方式看第 3 或第 4 节，第 5 节起为公共内容。

## 1. 环境要求

| 项目 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Linux（Ubuntu 22.04 / CentOS 8 及以上） | 单实例锁使用 `fcntl`，不支持 Windows 直接运行 |
| Docker 方式 | Docker Engine 24 以上，Docker Compose v2 | `docker compose version` 能输出即可；MySQL 由容器提供 |
| 裸机方式 | Python 3.12 及以上，MySQL 8.0（utf8mb4） | `pyproject.toml` 声明 `requires-python >= 3.12` |
| 内存 / 磁盘 | 建议 4 GB 内存起，磁盘按上传附件量预留 | 执行附件单文件上限 200 MB，任务产物在 `outputs/` 累积 |
| 出网 | 能访问所配置模型厂商的 API（当前 `api.openai.com`；接入其他厂商时相应放行） | 生成与评审模型走公网 API |
| 内网 | 无内网依赖 | 知识库 Embedding 同走 OpenAI（text-embedding-3-large）；接入私有化 Ollama 时在 `config/models.yaml` 的 `embeddings` 段配置 |
| 端口 | 对外 80（及 443）；应用 8000 仅本机或容器网络 | |

Redis 与 Celery 出现在依赖中，但 v1.0.x 的后台任务在进程内执行，不需要部署 Redis。

## 2. 目录规划与有状态数据

```
/opt/tiangong/              代码目录（git 检出版本标签）
├── .env                    环境变量（含密钥，权限 600，不入库）
├── config/models.yaml      运行时模型配置（首次启动自动生成，页面维护，不入库）
├── config/models.example.yaml  样例（入库）
├── outputs/                任务产物：上传原件、导出文件、执行附件、实例锁  ← 有状态
├── data/knowledge/         本地向量库（嵌入式 Qdrant）与知识文件         ← 有状态
├── logs/                   应用日志，按日滚动
└── backups/                数据库备份
```

三份有状态数据：MySQL 库、`outputs/`、`data/knowledge/`。备份与迁移都要覆盖这三处。`outputs/`、`data/`、`logs/`、`backups/`、`config/models.yaml` 都在 `.gitignore` 中，升级代码不会影响它们。

关于模型：LLM 模型不预置，首次启动生成的 `config/models.yaml` 模型清单为空，登录后在「系统设置 → 模型配置」添加；Embedding 段从样例复制，需要时手工编辑。详见第 5 节。

## 3. 方式一：Docker 部署

### 3.1 架构

```
浏览器 ──80/443──▶ nginx 容器（固定 IP 172.28.0.10）──▶ app 容器 :8000 ──▶ mysql 容器 :3306
                                                        ├─ ./outputs        上传原件 / 导出 / 执行附件 / 实例锁
                                                        ├─ ./data/knowledge 嵌入式向量库
                                                        ├─ ./logs
                                                        ├─ ./config         models.yaml（页面可改）
                                                        ├──▶ 内网 Ollama（可选；页面可添加私有化模型）
                                                        └──▶ 公网模型 API（OpenAI；DeepSeek / 智谱 / 百炼 … 可配）
```

- 应用只跑一个容器、一个进程。用户 / 项目 / 任务是进程内内存态加数据库回写，启动时在 `outputs/.instance.lock` 加文件锁，`--scale app=2` 或 `--workers` 都会被拒绝。
- 有状态数据全部在宿主机目录或命名卷：`mysql-data` 卷、`./outputs`、`./data`。镜像可随时重建。
- Nginx 固定 IP：应用只采信 `TIANGONG_TRUSTED_PROXIES` 所列地址转发的 `X-Forwarded-For`，且按精确 IP 匹配，所以 compose 给 nginx 容器固定 `172.28.0.10`，操作日志才能记录真实客户端 IP。
- `config/` 目录整体挂载：页面「模型配置」保存时原子替换 `models.yaml`，单文件挂载会失败，必须挂目录。

相关文件：`Dockerfile`、`.dockerignore`、`docker-compose.yml`、`docker/nginx.conf`、`.env.example`（末尾 Docker 专用段）。

### 3.2 获取代码

```bash
sudo mkdir -p /opt/tiangong && sudo chown $USER /opt/tiangong
cd /opt/tiangong
git clone <仓库地址> .
git checkout v1.0.3
```

### 3.3 写 `.env`

```bash
cp .env.example .env
chmod 600 .env
```

至少填写：

```bash
OPENAI_API_KEY=sk-xxxx                    # 页面上添加模型时填的密钥环境变量名，一个厂商一行
# ZHIPU_API_KEY=
TIANGONG_ADMIN_PASSWORD=<初始管理员口令>

MYSQL_ROOT_PASSWORD=<强密码>
MYSQL_PASSWORD=<强密码>
# HTTP_PORT=80
# TZ=Asia/Shanghai
```

不用填 `TIANGONG_DB_URL` 和 `TIANGONG_TRUSTED_PROXIES`，compose 已按容器网络写死。`MYSQL_PASSWORD` 会被拼进连接串，密码含 `@ # / % ?` 等符号也可以，应用会自动编码；但 compose 自身对 `$` 有特殊解释，密码里避免用 `$`。

### 3.4 创建数据目录并启动

```bash
mkdir -p outputs data/knowledge logs backups config
sudo chown -R 1000:1000 outputs data logs config    # 容器内用户 uid 1000
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

首次启动 MySQL 初始化约半分钟，app 容器等 mysql 健康检查通过后才启动。app 日志依次出现「数据库已连接」「未找到 …/config/models.yaml，已生成空模型清单」「服务启动」即完成建表。

### 3.5 验证

```bash
curl -s http://127.0.0.1/health                      # {"status":"ok"}
docker compose exec mysql mysql -utiangong -p"$MYSQL_PASSWORD" tiangong -e 'SHOW TABLES'
# kv_docs / entity_versions / recycle_bin / audit_log / ai_calls
```

浏览器打开 `http://<服务器IP>`，用 `admin` 与 `.env` 中的口令登录，然后按第 5 节配置模型。

### 3.6 Docker 方式的常用命令

| 事项 | 命令 |
|---|---|
| 状态与健康检查 | `docker compose ps`（app 显示 healthy） |
| 应用日志 | `docker compose logs -f app`，或宿主机 `logs/tiangong_<日期>.log` |
| 重启应用 | `docker compose restart app` |
| 改 `.env` 后（如新增模型密钥） | `docker compose up -d app`（重建容器才会读取新环境变量） |
| 手工改 `config/models.yaml` 后 | `docker compose restart app`（页面保存的配置无需重启） |
| 进入容器 | `docker compose exec app bash` |
| 数据库客户端 | `docker compose exec mysql mysql -utiangong -p tiangong` |
| 直连不经 Nginx | 在 compose 的 app 服务打开 `ports: "8000:8000"` |
| 启用 HTTPS | 证书放 `docker/certs/`，打开 compose 的 443 端口与 certs 挂载，启用 `docker/nginx.conf` 的 443 块 |
| Ollama 在宿主机上 | `models.yaml` 与页面里的地址写 `http://host.docker.internal:11434/v1`，compose 已映射该域名 |

## 4. 方式二：裸机部署

### 4.1 系统用户与代码

```bash
sudo useradd -r -m -d /opt/tiangong -s /bin/bash tiangong
sudo -iu tiangong
cd /opt/tiangong
git clone <仓库地址> .
git checkout v1.0.3
python3.12 -m venv .venv
source .venv/bin/activate
pip install --upgrade pip
pip install -e .
```

如服务器无法访问 PyPI，先在能出网的机器上 `pip download -d wheels -e .`，再把 `wheels/` 拷到服务器 `pip install --no-index --find-links wheels -e .`。

### 4.2 数据库

在 MySQL 中执行：

```sql
CREATE DATABASE tiangong CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'tiangong'@'%' IDENTIFIED BY '<强密码>';
GRANT ALL PRIVILEGES ON tiangong.* TO 'tiangong'@'%';
FLUSH PRIVILEGES;
```

数据库与应用同机时把 `'%'` 改为 `'127.0.0.1'`。不需要手工建表，应用首次启动自动创建。

### 4.3 环境变量 `.env`

```bash
cp .env.example .env
chmod 600 .env
```

编辑 `.env`：

```bash
# 数据库。密码可直接写原文，含 @ # / % 等符号也无需编码（应用自动处理；已编码的写法同样可用）
TIANGONG_DB_URL=mysql+pymysql://tiangong:<密码>@127.0.0.1:3306/tiangong?charset=utf8mb4

# 模型密钥：页面上添加模型时填的环境变量名，一个厂商一行
OPENAI_API_KEY=sk-xxxx
# DEEPSEEK_API_KEY=
# ZHIPU_API_KEY=

# 初始管理员口令。不设置则首启生成随机口令打印在日志（仅一次）并强制首登改密
TIANGONG_ADMIN_PASSWORD=<初始口令>

# 反向代理 IP，逗号分隔。只有来自这些地址的请求才采信 X-Forwarded-For，审计日志才能记到真实客户端 IP
TIANGONG_TRUSTED_PROXIES=127.0.0.1

# 以下保持默认即可
# TIANGONG_EXPOSE_DOCS=false          # OpenAPI 文档，生产关闭
# TIANGONG_LOG_LEVEL=INFO
# TIANGONG_SESSION_TTL_HOURS=72
# TIANGONG_LOG_RETENTION_DAYS=180     # AI 调用日志与操作日志保留天数
# TIANGONG_MAX_UPLOAD_SIZE_MB=50      # 需求附件单文件上限
# TIANGONG_LLM_MAX_CONCURRENCY=4
```

全部配置项见 `app/config.py`，环境变量名为 `TIANGONG_` 加字段名大写。

### 4.4 一键脚本启停（推荐）

`scripts/server.sh` 是源码部署的一键脚本，配置只改 `.env`，不依赖 systemd / Docker：

```bash
cd /opt/tiangong
bash scripts/server.sh start      # 后台启动，等待 /health 通过（含建表与数据迁移，最多等 90 秒）
bash scripts/server.sh status     # 进程、端口、运行时长、健康检查
bash scripts/server.sh logs       # 跟踪 logs/server.out
bash scripts/server.sh restart    # 改 .env 后执行
bash scripts/server.sh stop       # 优雅停止，最多等 20 秒后强杀
bash scripts/server.sh update     # 拉取当前分支最新代码，依赖有变化时重装，然后重启
```

要点：

- 监听地址与端口在 `.env` 里用 `TIANGONG_HOST` / `TIANGONG_PORT` 指定，默认 `0.0.0.0:8000`；走 Nginx 时 HOST 填 `127.0.0.1`。
- 脚本不 `source .env`，数据库口令含 `# $ @` 等符号也不受影响；模型清单在页面维护，保存即生效，不用重启。
- 重复 `start` 不会起第二个实例；应用自身也有实例锁，同一数据目录只允许一个进程。
- 进程输出在 `logs/server.out`（超过 50MB 自动轮转一次），应用按日日志在 `logs/tiangong_<日期>.log`。
- 脚本不会随系统开机自启；需要开机自启或崩溃自动拉起时用 4.5 节的 systemd，两种方式二选一，不要同时用。

首次启动后验证：

```bash
curl -s http://127.0.0.1:8000/health          # {"status":"ok"}
mysql -u tiangong -p tiangong -e 'SHOW TABLES' # kv_docs / entity_versions / recycle_bin / audit_log / ai_calls
```

浏览器打开 `http://<服务器IP>:8000`，用 `admin` 与 `.env` 里的口令登录，然后按第 5 节配置模型。

### 4.5 systemd 托管（可选）

`/etc/systemd/system/tiangong.service`：

```ini
[Unit]
Description=TianGong AI Test Case Platform
After=network.target mysql.service

[Service]
Type=simple
User=tiangong
Group=tiangong
WorkingDirectory=/opt/tiangong
EnvironmentFile=/opt/tiangong/.env
ExecStart=/opt/tiangong/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --timeout-graceful-shutdown 10
Restart=on-failure
RestartSec=5
TimeoutStopSec=20
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now tiangong
sudo systemctl status tiangong
journalctl -u tiangong -f
```

要点：

- **只能单进程**。不要加 `--workers`，也不要同时启动第二个实例。应用启动时在 `outputs/.instance.lock` 加文件锁，第二个实例会直接报错退出。
- 走 Nginx 时应用绑定 `127.0.0.1`；不用 Nginx 直接对内网提供服务则改为 `0.0.0.0`。
- `--timeout-graceful-shutdown 10`：停止或重启时最多等 10 秒，不被长耗时的 PDF 图片理解请求卡住。
- `scripts/dev.sh` 是本地开发脚本，会去拉起本地 MySQL，服务器上不要用它。

### 4.6 Nginx 反向代理

`/etc/nginx/conf.d/tiangong.conf`：

```nginx
server {
    listen 80;
    server_name tiangong.example.com;

    # 执行附件上限 200 MB，留余量
    client_max_body_size 210m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # AI 分析、拆解、生成为后台任务，页面轮询获取进度；但附件解析上传与导出仍可能较慢
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_request_buffering off;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

`.env` 中 `TIANGONG_TRUSTED_PROXIES` 必须填 Nginx 所在 IP（同机为 `127.0.0.1`），否则操作日志里记录的都是代理地址。需要 HTTPS 时按常规方式加证书，应用侧无需改动。

## 5. 模型配置（两种方式相同）

LLM 模型不预置，首次启动自动生成 `config/models.yaml`（模型清单为空，不入库）。登录后在「系统设置 → 模型配置」添加：

| 字段 | 填法 |
|---|---|
| 名称 | 系统内唯一标识，任务创建时下拉显示 |
| 厂商 | openai / deepseek / zhipu / dashscope / ollama / vllm 等，自由填写；OpenAI 官方 API 必须填 `openai`（GPT-5 系参数格式不同，客户端据此适配） |
| Base URL | OpenAI 兼容地址，如 `https://api.openai.com/v1`、`https://api.deepseek.com/v1` |
| 厂商侧模型名 | 厂商文档里的模型编码，原样填（如 `gpt-6-sol`、`deepseek-chat`） |
| 密钥环境变量名 | 形如 `XXX_API_KEY`，填的是变量名，密钥值写在 `.env`；内网无鉴权服务留空 |
| 支持 Vision | 图片需求与 PDF 内嵌图会自动路由到勾选的模型，至少配一个 |
| 降级链路 | 备用模型名，须先添加备用模型再引用 |

第一个添加的模型自动成为默认。密钥写入 `.env` 后要重启服务（Docker 方式 `docker compose up -d app`），页面「密钥」列显示「已配置」后用「连通性测试」验证；测试只测该模型本身，不走降级链路。

Embedding（知识库向量化）不在页面管理，生成的 `models.yaml` 会从样例复制 `embeddings` 段，默认为 OpenAI text-embedding-3-large（与 LLM 共用 `OPENAI_API_KEY`）。换用其他厂商或内网 Ollama 时编辑该段后重启；Embedding 模型一经确定不要更换，向量维度变化会导致已入库知识无法检索。知识库功能依赖它，用例生成不依赖。

## 6. 从本地环境迁移数据

把开发机上的现有数据搬到服务器时，三处一起迁。在开发机导出：

```bash
cd <本地仓库>
TIANGONG_DB_URL=<本地库连接串> scripts/migrate_prod.sh    # 备份到 backups/tiangong-<时间>.sql.gz
tar czf outputs.tgz outputs
tar czf knowledge.tgz data/knowledge
```

**Docker 方式**（先只起数据库导入，再解开目录，最后启动全部）：

```bash
cd /opt/tiangong
docker compose up -d mysql
gunzip -c tiangong-<时间>.sql.gz | docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" tiangong
tar xzf outputs.tgz && tar xzf knowledge.tgz
rm -f outputs/.instance.lock
sudo chown -R 1000:1000 outputs data
docker compose up -d --build
```

**裸机方式**（应用未启动状态）：

```bash
gunzip -c tiangong-<时间>.sql.gz | mysql -u tiangong -p tiangong
tar xzf outputs.tgz -C /opt/tiangong
tar xzf knowledge.tgz -C /opt/tiangong
chown -R tiangong:tiangong /opt/tiangong/outputs /opt/tiangong/data
rm -f /opt/tiangong/outputs/.instance.lock
sudo systemctl start tiangong
```

启动日志会输出「M4 执行迁移 N 个任务」「M2 需求迁移 N 个任务」，这是旧任务制数据到需求 / 计划实体的自动迁移，幂等，可重复启动。迁移后以管理员登录，`scripts/migrate_prod.sh --check <token>` 或打开 项目管理 →（未指定），把仍未归属项目的遗留任务逐个「归属项目」，报告显示「已完成」即迁移闭合。全新部署无历史数据时跳过本节。

## 7. 备份与恢复

每日备份脚本 `/opt/tiangong/backups/daily.sh`（crontab `0 2 * * *`）。

**Docker 方式**：

```bash
#!/usr/bin/env bash
set -e
cd /opt/tiangong
set -a; . ./.env; set +a
D=backups/$(date +%F); mkdir -p "$D"
docker compose exec -T mysql mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --default-character-set=utf8mb4 tiangong | gzip > "$D/db.sql.gz"
tar czf "$D/outputs.tgz" outputs --exclude=.instance.lock
tar czf "$D/knowledge.tgz" data/knowledge
find backups -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +
```

**裸机方式**：

```bash
#!/usr/bin/env bash
set -e
D=/opt/tiangong/backups/$(date +%F)
mkdir -p "$D"
mysqldump -u tiangong -p'<密码>' --single-transaction --default-character-set=utf8mb4 tiangong | gzip > "$D/db.sql.gz"
tar czf "$D/outputs.tgz" -C /opt/tiangong outputs --exclude=.instance.lock
tar czf "$D/knowledge.tgz" -C /opt/tiangong data/knowledge
find /opt/tiangong/backups -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +
```

恢复：停应用（`docker compose stop app` 或 `systemctl stop tiangong`），按第 6 节的顺序导入数据库并解开两个目录，再启动。

## 8. 升级

升级前先跑一次备份。表结构变更与数据迁移在应用启动时自动、幂等执行，不需要手工执行 SQL。

**Docker 方式**：

```bash
cd /opt/tiangong
bash backups/daily.sh
git fetch --tags && git checkout -f v1.0.4      # 目标版本标签
docker compose up -d --build app                # 只重建应用镜像，mysql / nginx 不动
docker compose logs -f app
```

**裸机方式（一键脚本）**：跟分支部署时一条命令完成拉取、按需重装依赖、重启：

```bash
cd /opt/tiangong
bash scripts/server.sh update
```

跟版本标签部署时先切标签再重启：

```bash
cd /opt/tiangong
git fetch --tags && git checkout -f v1.0.4
.venv/bin/pip install -e .                      # 依赖有变化时
bash scripts/server.sh restart
```

**裸机方式（systemd 托管）**：

```bash
sudo systemctl stop tiangong
sudo -iu tiangong
cd /opt/tiangong
git fetch --tags && git checkout -f v1.0.4
source .venv/bin/activate && pip install -e .   # 依赖有变化时
exit
sudo systemctl start tiangong
journalctl -u tiangong -n 50
```

`git checkout -f` 会丢弃对已跟踪文件的本地改动；`.env`、`outputs/`、`data/`、`config/models.yaml` 都不是跟踪文件，不受影响。回滚时切回旧标签重新启动，必要时用备份恢复数据库。

## 9. 日常运维

| 事项 | 位置 / 方法 |
|---|---|
| 应用日志 | `logs/tiangong_<日期>.log`，按日滚动；Docker 用 `docker compose logs -f app`，裸机用 `journalctl -u tiangong` 看启动错误 |

## 10. 常见问题

**局域网其他机器访问不到。** 裸机方式 uvicorn 默认只监听 `127.0.0.1`，直连需 `--host 0.0.0.0`，走 Nginx 则应用保持 `127.0.0.1`。Docker 方式默认只暴露 Nginx 的 80 端口，直连要在 compose 打开 app 的 `ports`。

**启动报「检测到另一个天工实例正在使用同一数据目录」。** 已有进程在运行（常见于宿主机裸机版和容器版同时跑），或上次异常退出后锁文件残留。确认无进程后删除 `outputs/.instance.lock` 再启动。

**数据库连接失败，主机名变成 `@@127.0.0.1`。** 服务器代码版本低于 v1.0.1，不支持密码里的 `@`。升级到 v1.0.1 以上，或把密码 URL 编码后写入连接串（`@` 写 `%40`）。

**启动报「模型配置文件不存在」。** 代码版本低于 v1.0.1 且 `config/models.yaml` 被删。升级后启动会自动生成。

**app 容器启动报 Permission denied。** 宿主机目录属主不是 uid 1000，执行 `sudo chown -R 1000:1000 outputs data logs config`。

**页面「模型配置」保存报错或不生效（Docker）。** `config/` 必须整目录挂载，单文件挂载 `models.yaml` 会让原子替换失败。

**模型连通性测试失败「密钥环境变量未设置」。** `.env` 只在启动时读取，写入密钥后要重启（Docker 方式 `docker compose up -d app`）。变量名须形如 `XXX_API_KEY`，页面填的是变量名不是密钥。

**模型厂商返回「模型不存在」。** 「厂商侧模型名」要和厂商文档的模型编码完全一致，含连字符与大小写（如 `glm-4.5` 而非 `glm4.5`）。

**知识库上传或检索报错。** 多为 `OPENAI_API_KEY` 未配或出网受限；若 `embeddings` 段改接了内网 Ollama，用 `curl <地址>/models` 验证地址后修改并重启。

**上传大附件返回 413。** Nginx 的 `client_max_body_size` 小于文件大小，裸机改 `/etc/nginx/conf.d/tiangong.conf`，Docker 改 `docker/nginx.conf` 后 `docker compose restart nginx`。

**操作日志里的 IP 都是代理地址。** 裸机未设置 `TIANGONG_TRUSTED_PROXIES` 或与 Nginx 实际地址不一致；Docker 方式确认 `docker inspect tiangong-nginx` 的 IP 是 `172.28.0.10`。

**MySQL 容器一直 unhealthy。** 首次初始化未完成，或 `MYSQL_ROOT_PASSWORD` 与已有 `mysql-data` 卷里的口令不一致。全新部署可 `docker compose down -v` 清卷重来；有数据时不要带 `-v`。

**首次登录提示必须修改密码。** 未设置 `TIANGONG_ADMIN_PASSWORD` 时的预期行为，随机口令只在首次启动日志打印一次，`grep 初始管理员 logs/tiangong_*.log` 可找回。

## 11. 安全建议

- `.env` 权限 600；密钥不要写进 `models.yaml` 或提交到仓库。
- 应用只监听本机或容器网络，由 Nginx 对外并启用 HTTPS；防火墙 / 云安全组只放行 80/443，不要把 8000 直接暴露到公网。
- MySQL 不对公网开放，应用账号只授权 `tiangong` 库。
- 生产保持 `TIANGONG_EXPOSE_DOCS=false`。
- 定期检查「操作日志」中的登录失败记录，管理员账号建议开启两步验证。
