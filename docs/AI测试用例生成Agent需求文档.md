## 1. 项目背景与目标

### 1.1 背景

在软件测试工作中，测试用例编写占据测试人员大量的工时。需求文档形式多样（PDF、Word、图片/截图、原型图等），人工阅读需求、拆解测试点、编写用例的过程重复度高、效率低，且用例质量高度依赖测试人员的个人经验，覆盖度参差不齐。

随着大语言模型（LLM）能力的成熟，可以构建一个**专业测试专家 Agent**，自动完成"需求理解 → 测试点拆解 → 用例生成 → 标准格式输出"的全流程，显著提升测试用例编写效率与覆盖度。

### 1.2 项目目标

1. 构建以"资深测试专家"为核心角色的**多 Agent 协作系统**：主控、需求分析、用例生成、评审、知识管家、学习六类 Agent 分工协作，通过预定义的有向图编排完成"需求理解 → 测试点拆解 → 用例生成 → 独立评审 → 标准输出"全流程。
2. 通过统一的 API 抽象层，支持接入各类主流大模型（OpenAI、Claude、DeepSeek、通义千问、文心一言、本地私有化模型等），可灵活切换与配置。
3. 支持多种需求输入形式：PDF、Word（doc/docx）、图片（截图、原型图、流程图）、纯文本等。
4. 支持用户自定义测试用例模板，Agent 严格按模板字段与规范生成用例。
5. 输出两种标准交付物：**XMind 脑图文件（.xmind）** 与 **表格文件（.xlsx / .csv）**。
6. 构建**业务知识库（RAG）**，沉淀业务规则、历史需求、历史用例、领域术语等知识，在用例生成时自动检索并注入相关业务上下文，使生成的用例具备业务针对性，而非仅通用测试方法覆盖。

### 1.3 预期收益

- 单个需求的用例初稿编写时间从小时级缩短至分钟级，效率提升 70% 以上。
- 通过测试专家 Prompt 体系与用例设计方法论（等价类、边界值、场景法、判定表、错误推测等）内置，提升用例覆盖度与一致性。
- 生成结果直接兼容团队现有测试管理流程（XMind 评审 + Excel 导入测试平台）。

## 2. 名词解释

| 术语 | 说明 |
|---|---|
| Agent | 以 LLM 为核心、具备角色设定/工具调用/流程编排能力的智能体。本系统为多 Agent 协作架构 |
| 主控 Agent（Orchestrator） | 负责任务编排与用户对话的调度者，决定何时调用哪个专职 Agent |
| 评审 Agent（Critic） | 独立于生成者的质量检查角色，与生成 Agent 使用不同 Prompt（可用不同模型），负责自检、合规校验与打分 |
| 有向图编排 | Agent 间协作路径预定义（拆解→生成→评审→修正循环），非开放式自由对话，保证可控可调试 |
| LLM 适配层 | 屏蔽不同大模型 API 差异的统一接入层 |
| 需求解析 | 将 PDF/Word/图片等原始需求转换为结构化文本的过程 |
| 用例模板 | 用户提供的测试用例字段规范（如：用例编号、模块、前置条件、步骤、预期结果、优先级等） |
| OCR / 多模态识别 | 对图片类需求进行文字与结构信息提取的能力 |
| RAG | 检索增强生成（Retrieval-Augmented Generation），生成前先从知识库检索相关内容注入模型上下文 |
| 业务知识库 | 由三大分类组成的可检索知识仓库：①测试用例库 ②需求文档库（历史 PRD）③玩法/业务规则库（游戏玩法说明或业务说明与业务流程） |
| Embedding / 向量化 | 将文本转换为向量以支持语义检索的技术 |
| 记忆系统 | Agent 自动积累的个性化经验，含短期会话记忆与长期记忆（用户偏好、项目上下文、修改习惯），与知识库互补 |
| LLM-as-Judge | 用大模型作为评估器对生成结果自动打分的技术，评估标准以人工评审数据校准 |
| SFT / LoRA | 有监督微调 / 低秩适配微调，利用积累的高质量语料对私有化模型进行能力增强 |
| 黄金评估集 | 人工精标的固定评测样本集，任何 Prompt/模型变更上线前的回归基准，防止能力退化 |

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 测试工程师 | 主要使用者 | 上传需求，快速获得高质量用例初稿 |
| 测试负责人 | 用例评审者 | 用例格式统一、覆盖度可评估、可导出评审 |
| 平台管理员 | 系统维护者 | 配置模型、管理模板、监控用量与成本 |

### 3.2 典型使用场景

1. **场景一**：测试工程师上传一份 PDF 需求文档与团队用例模板，选择内部私有化大模型（或已配置的采购商用模型），一键生成 XMind 脑图与 Excel 用例表。
2. **场景二**：测试工程师上传原型图截图（图片），Agent 通过多模态模型识别页面元素与交互逻辑，生成 UI 功能测试用例。
3. **场景三**：需求包含多个附件（Word 主文档 + 若干接口截图），Agent 合并解析后统一生成完整用例集。
4. **场景四**：用户对生成结果不满意，通过多轮对话补充需求上下文（如"增加异常场景""补充兼容性用例"），Agent 增量修订并重新导出。
5. **场景五（玩法/业务规则库）**：测试负责人预先将"游戏玩法说明、战斗与数值规则、道具/经济系统规则"（或非游戏业务的业务说明与流程文档）导入知识库；后续新活动/新玩法需求生成用例时，Agent 自动检索并引用这些规则，生成的用例能覆盖如"活动积分达到上限后的处理""道具消耗与背包容量边界""跨玩法数值联动（新活动奖励是否突破原有等级上限）"等业务规则类场景。
6. **场景六（需求文档库）**：将以往的需求 PRD 导入知识库，新需求生成用例时 Agent 参考历史 PRD 中的既有功能逻辑与业务约定，识别新旧功能的关联影响点，补充回归与兼容类用例。
7. **场景七（测试用例库）**：将历史测试用例导入知识库，生成时 Agent 对齐团队既有用例的风格与粒度，并比对同类模块历史用例进行覆盖度查漏；评审通过的优质用例一键回存测试用例库，知识随使用不断积累。
8. **场景八（记忆系统）**：测试工程师上月在某游戏项目中多次要求"用例步骤精简到 5 步以内、必须补充断线重连场景"；本月针对该项目新玩法创建任务时，Agent 自动应用这些偏好与项目背景，首稿即符合个人习惯，无需重复调教。

### 4.1a 多 Agent 角色分工与协作规则

| Agent 角色 | 职责 | 承载的功能需求 | 运行方式 |
|---|---|---|---|
| 主控 Agent（Orchestrator） | 与用户对话、任务编排、决定调用哪个专职 Agent、汇总最终结果 | F-3-5 多轮修订入口、任务状态管理 | 在线，任务全程 |
| 需求分析 Agent | 文档/图片理解、需求结构化、测试点拆解、疑似需求盲区识别 | F-2-x 解析链路、F-3-3 测试点拆解、F-3-7 部分 | 在线，任务前段 |
| 用例生成 Agent | 按模板 + 注入知识 + 记忆生成详细用例；承载测试专家角色与用例设计方法论 | F-3-1/2/4、F-4-5 生成侧 | 在线，可按模块并行多实例 |
| 评审 Agent（Critic） | 独立自检、模板合规校验、基于测试用例库的覆盖度比对、LLM-as-Judge 打分；与生成 Agent 分离，可配置不同模型 | F-3-6、F-4-5 校验侧、F-9-2、F-7-3b 中用例库比对 | 在线，生成后强制执行 |
| 知识管家 Agent | 三大知识库检索编排、5:3:2 配额分配与让渡、知识与需求冲突仲裁、知识快照记录 | F-7-3b/4/5/12/13 | 在线，贯穿拆解与生成阶段 |
| 学习 Agent | 坏案例归因、Prompt 优化候选生成、逃逸缺陷学习、记忆提炼 | F-9-1/3/4/5、F-8-5 | **离线异步**，任务结束后/定时运行 |

**协作规则（有向图编排，非自由对话）**：
1. Agent 间协作路径预定义：拆解 → 生成 → 评审 → （不合格）修正回环（最多 3 轮）→ 输出。不采用开放式多 Agent 自由讨论，保证结果可控、链路可调试、成本可预期。
2. **生成与评审强制分离**：评审 Agent 使用独立 Prompt（可配置不同模型），避免生成者"自我辩护"；评审不通过的用例带具体问题打回生成 Agent 定点修正，而非全量重生成。
3. **上下文隔离**：每个 Agent 只接收自身职责所需的上下文——测试用例库的历史用例只注入评审 Agent（覆盖度比对）与拆解阶段，不挤占生成 Agent 上下文；5:3:2 配额由知识管家 Agent 统一调度。
4. **并行加速**：大需求经需求分析 Agent 按功能模块切分后，多个用例生成 Agent 实例并行生成，评审 Agent 汇总校验全局一致性（编号连续、模块无重叠遗漏）。
5. **学习 Agent 与在线链路解耦**：归因、Prompt 优化、记忆提炼均离线异步执行，不增加用户任务的等待时间。
6. 每次任务记录完整的 Agent 调用链路（谁在哪一步产出/修改了什么），支撑问题排查与归因分析。

### 4.4 模块三：测试专家 Agent 核心（P0）

> 本模块功能由多 Agent 协作承载（角色分工见 4.1a）：F-3-1/2/4 由用例生成 Agent 承载，F-3-3 由需求分析 Agent 承载，F-3-6 由独立的评审 Agent（Critic）承载，F-3-5 由主控 Agent 承载。

| 编号 | 需求项 | 详细说明 | 优先级 |
|---|---|---|---|
| F-3-1 | 测试专家角色设定 | 用例生成 Agent 内置资深测试专家 System Prompt：具备功能测试、接口测试、UI 测试、异常测试、边界测试、兼容性、安全性等用例设计经验 | P0 |
| F-3-2 | 用例设计方法论内置 | 生成用例时综合运用：等价类划分、边界值分析、判定表、因果图、场景法（正常流+异常流）、错误推测法、正交实验法 | P0 |
| F-3-3 | 测试点拆解 | 需求分析 Agent 先输出"功能模块 → 测试点"两级拆解结构，供用户确认后再展开为详细用例（可配置跳过确认）；拆解阶段联动知识管家 Agent 比对测试用例库做覆盖度查漏 | P1 |
| F-3-4 | 用例类型覆盖 | 支持指定生成的用例类型范围：功能/接口/UI/异常/边界/兼容性/安全/性能建议项 | P1 |
| F-3-5 | 多轮对话修订 | 主控 Agent 支持基于已生成结果进行对话式增删改（"补充XX模块的异常用例""将优先级规则调整为XX"），保留会话上下文，并将修订指令路由至对应的生成/评审 Agent | P0 |
| F-3-6 | 独立评审自检 | **评审 Agent（Critic）**在生成后强制执行：字段完整性、步骤与预期结果对应性、编号连续性、明显异常场景遗漏检查；评审 Agent 与生成 Agent 使用独立 Prompt（可配置不同模型），不合格项带具体问题打回定点修正（最多 3 轮回环） | P1 |
| F-3-7 | 覆盖度报告 | 输出用例统计摘要：模块数、用例总数、各优先级/类型分布、疑似需求盲区提示 | P2 |

| F-5-2 | Excel 输出 | 按用户模板生成 .xlsx 文件，含表头样式、列宽自适应、优先级条件着色 | P0 |
| F-5-3 | CSV 输出 | 提供 UTF-8 with BOM 编码的 CSV，便于导入禅道、TestLink、Jira 等测试管理平台 | P1 |
| F-5-4 | 双格式同步导出 | 单次任务默认同时产出 XMind + 表格两种文件，内容保持一致 | P0 |
| F-5-5 | 文件下载与留存 | 生成文件支持在线下载；任务历史保留 30 天（可配置），支持重新下载 | P1 |

### 4.7 模块六：任务与系统管理（P1）

| 编号 | 需求项 | 详细说明 | 优先级 |
|---|---|---|---|
| F-6-1 | 任务管理 | 任务创建、进度展示（解析中/生成中/自检中/已完成/失败）、历史任务列表与检索 | P1 |
| F-6-2 | 异步任务队列 | 长任务异步执行（Celery/消息队列），支持并发任务与排队机制 | P1 |
| F-6-3 | 用户与权限 | 用户登录鉴权（账号密码/SSO）；权限模型为**系统级两角色（普通用户/管理员）+ 项目级成员制**：知识空间、项目记忆、任务数据均按项目成员隔离，与 F-7-11、F-8-8 的隔离要求配套 | P1 |
| F-6-4 | OpenAPI 对外接口 | 系统自身提供 RESTful API（创建任务/查询状态/下载结果），支持与 Jenkins、DevOps 流水线集成 | P2 |

| F-6-7 | 效果度量看板 | 内置度量看板：用例采纳率、人工修改率、提效比、知识库命中率等核心指标，按项目/时间维度统计 | P2 |
| F-6-8 | 离线评审终稿回传 | **闭环兜底通道**：用户下载 Excel 离线评审后，可将评审终稿回传，系统自动与 AI 原稿做逐条 diff（新增/修改/删除/未动），生成等效评审留痕。保证"下载-离线评审"的既有工作流不脱离度量与学习闭环；回传入口在任务详情页常驻提醒 | P1 |

### 4.8 模块七：业务知识库（RAG）（P0）

> 设计目的：测试用例的质量高度依赖业务知识（业务规则、字段校验逻辑、上下游依赖、历史缺陷经验等）。仅凭单份需求文档，LLM 无法掌握业务全貌。知识库使 Agent 在生成用例前先"学习"相关业务背景，生成结果从"通用用例"升级为"懂业务的用例"。
>
> **知识库三大分类（已确认）**：
>
> | 分类 | 内容 | 在用例生成中的作用 |
> |---|---|---|
> | ① 测试用例库 | 历史测试用例（Excel/XMind 导入）及评审后回存的优质用例 | 提供用例风格、粒度、步骤描述规范的参考范例；同类模块用例作为覆盖度基线，避免遗漏既有场景 |
> | ② 需求文档库 | 以往的需求 PRD 文档 | 提供既有功能逻辑与业务约定，识别新旧需求的关联影响点，支撑回归与兼容类用例生成 |
> | ③ 玩法/业务规则库 | 游戏玩法说明、游戏规则（数值、战斗/关卡、道具与经济系统、活动规则），或非游戏业务的业务说明与业务流程文档 | 提供业务规则与流程约束，支撑数值边界类、规则冲突类、流程分支类用例生成 |

| 编号 | 需求项 | 详细说明 | 优先级 |
|---|---|---|---|
| F-7-1 | 知识文档上传 | 支持上传业务知识文档：PDF、Word、Excel、Markdown、TXT、图片（复用需求解析模块的解析能力）；上传时须归属到三大分类之一 | P0 |
| F-7-2 | 测试用例库入库 | 支持将历史测试用例（Excel/XMind）导入**测试用例库**，按模块结构化存储（模块-测试点-用例），作为用例风格、粒度与业务场景覆盖的参考范例 | P0 |
| F-7-3 | 知识分类管理 | 按知识空间/项目/游戏组织知识，每个知识空间下固定包含三大分类：**测试用例库、需求文档库、玩法/业务规则库**；支持标签、检索、编辑、删除、版本更新（更新后自动重新向量化） | P0 |
| F-7-3a | 规则知识结构化增强 | 针对玩法/业务规则库文档，入库时可提取结构化要素：玩法/流程名称、触发条件、数值规则与边界（如等级上限、掉率、消耗公式）、状态流转、限制条件。生成用例时优先注入，支撑数值边界类与规则冲突类用例的生成 | P1 |
| F-7-3b | 分类差异化检索与注入 | 三大分类在生成流程中的检索时机不同：玩法/业务规则库与需求文档库在**用例生成前**检索注入（提供业务上下文）；测试用例库在**测试点拆解阶段**即检索注入（对齐风格粒度、比对历史用例做覆盖度查漏——提前到拆解阶段可在用例展开前发现遗漏，避免生成完才返工），并在自检阶段复核。知识注入配额**按任务全生命周期的知识 token 总预算 5:3:2 分配：测试用例库 50%、需求文档库 30%、玩法/业务规则库 20%**，比例支持管理员按项目调整；当某类库检索相似度普遍低于阈值（如全新玩法无历史用例可参考）时，其配额自动让渡给其他库，避免上下文浪费 | P1 |
| F-7-4 | 向量化与语义检索 | 知识入库后自动切片（Chunking）并向量化存储；生成用例前基于需求内容进行语义检索（Top-K + 相似度阈值），支持向量检索与关键词检索混合（Hybrid Search） | P0 |
| F-7-5 | 知识自动注入 | 检索到的相关知识自动注入 Agent 生成上下文；注入内容对用户可见（本次引用了哪些知识片段），保证可解释性 | P0 |
| F-7-6 | 知识范围选择 | 创建任务时可指定引用的知识空间（如"XX游戏知识空间"），也可选择不使用知识库 | P1 |
| F-7-7 | 领域术语表 | 支持维护结构化术语表（术语-释义-业务规则），生成时优先注入，统一用例中的业务用语 | P1 |
| F-7-8 | 缺陷经验沉淀 | 历史缺陷经验统一沉淀至**玩法/业务规则库**（以规则条目形式存储，不新设分类）：支持人工导入禅道/Jira 缺陷记录提炼，也接收 F-9-5 逃逸缺陷自动学习产出的规则草稿（人工确认后生效）。生成时参考同类模块的缺陷经验，强化易错场景覆盖 | P2 |
| F-7-9 | 知识反哺闭环（防污染约束） | 评审确认后的优质用例可一键回存**测试用例库**，形成"生成 → 评审 → 沉淀 → 更优生成"闭环。**防同质化约束**：回存用例强制标记来源（AI 生成+人工评审 / 纯人工编写），检索注入时两类来源按可配比例混合（默认纯人工来源优先），防止"AI 参考 AI"导致用例风格与覆盖思路逐渐同质化退化 | P2 |
| F-7-10 | Embedding 模型配置 | 向量化模型可配置，**优先使用内网私有化 Embedding 模型**（bge、m3e 等，可与私有化大模型同集群部署），与 LLM 适配层统一管理 | P1 |
| F-7-11 | 知识权限隔离 | 知识空间支持团队/项目级权限隔离，避免跨业务线数据泄露 | P1 |
| F-7-12 | 知识与需求冲突仲裁 | 当检索到的知识与当前需求内容矛盾时（如知识库记载"等级上限 60"而新需求写"上限提升至 80"），**以当前需求为准**，但 Agent 须显式标注冲突点并提示"此处为疑似规则变更，建议作为重点测试对象"（新旧规则切换处恰是高风险区，如老玩家数据兼容、跨系统联动）。冲突记录同时反馈知识库管理员，作为知识更新线索（联动 R7 知识时效性维护） | P1 |
| F-7-13 | 任务知识快照 | 每次生成任务记录本次实际注入的知识片段清单及其版本快照。用途：①归因分析（F-9-4）判断"知识过期/检索未命中"需要还原当时注入内容；②历史任务可追溯"当时为什么这么生成"；③知识更新后重跑任务的差异可解释 | P1 |

### 4.9 模块八：记忆系统（P1）

> 设计目的：让 Agent "越用越懂你"。与知识库的区别：**知识库是团队共享的业务知识，需要主动上传维护；记忆是 Agent 在使用过程中自动积累的个性化经验**（用户偏好、修改习惯、项目上下文），无需用户显式维护。两者互补，共同提升生成质量。

| 编号 | 需求项 | 详细说明 | 优先级 |
|---|---|---|---|
| F-8-1 | 短期记忆（会话记忆） | 单任务多轮对话的完整上下文记忆：已生成的用例、用户的修订指令、确认过的测试点结构，保证多轮修订不丢失、不重复提问已确认的信息 | P0 |
| F-8-2 | 用户偏好记忆 | 跨会话记住用户的个性化偏好：常用模板、默认模型、用例粒度偏好（步骤详细/精简）、优先级判定习惯、常用的修订指令模式（如该用户总要求"补充兼容性用例"则后续主动生成） | P1 |
| F-8-3 | 项目记忆 | 按项目维度记忆上下文：项目/游戏的模块结构、术语约定、历史任务的需求脉络。同一项目的新任务自动继承项目记忆，无需重复介绍背景 | P1 |
| F-8-4 | 修改习惯学习 | 基于评审留痕数据（F-6-6/F-6-8），提炼高频修改模式并记忆（如"预期结果必须包含具体数值""步骤不超过 8 步"）。**分工仲裁**：仅个人/项目维度的习惯写入记忆；当同一模式在多个用户间普遍出现（跨用户共性），移交自我学习模块（F-9-3）升级为 Prompt 级约束，同时从个人记忆中去重下线，避免同一规则在记忆与 Prompt 中重复注入 | P1 |
| F-8-5 | 记忆自动提炼 | 会话结束或任务完成后，Agent 自动从对话中提炼值得长期记忆的信息（偏好、纠正、项目事实），经压缩摘要后写入长期记忆，避免原始对话堆积 | P1 |
| F-8-6 | 记忆可见可控 | 用户可查看 Agent 记住了哪些关于自己/项目的内容，支持编辑、删除单条记忆或一键清空；生成时引用了哪些记忆对用户可见（可解释性） | P0 |
| F-8-7 | 记忆检索与注入 | 生成任务时自动检索相关记忆（用户偏好 + 当前项目记忆）注入上下文；记忆注入不占用三大知识库的 5:3:2 配额，单独预留少量固定配额（建议 ≤ 上下文的 5%-10%） | P1 |
| F-8-8 | 记忆隔离与安全 | 用户记忆仅本人可见；项目记忆随项目权限隔离；记忆内容不跨团队共享 | P0 |
| F-8-9 | 记忆时效管理 | 长期未命中或与新记忆冲突的旧记忆自动降权/归档；项目结项支持记忆归档 | P2 |

### 4.10 模块九：自我学习与进化（P1）

> 设计目的：让系统的生成质量随使用**自动**提升，而非只依赖人工调优。与已有能力的关系与分工：**记忆系统**学习"个体偏好"（用户/项目维度），**知识库反哺**积累"团队知识"（内容维度），**自我学习模块**进化"系统本身"（Prompt、评估标准、模型参数——能力维度）。三者共同构成数据飞轮。

| 编号 | 需求项 | 详细说明 | 优先级 |
|---|---|---|---|
| F-9-1 | 学习语料自动积累 | 将评审留痕（在线评审 F-6-6 或离线回传 diff F-6-8）自动加工为标准化学习语料：〈需求输入 + 注入知识快照（F-7-13）+ 多轮修订指令序列 + AI 终稿 + 人工终稿 + 逐条操作标签 + 修改差异〉。**口径定义：AI 终稿 = 用户最后一轮修订指令后的 AI 输出**（多轮修订中用户的指令本身也是有价值语料，体现了 Prompt 应默认覆盖的诉求）；人工终稿 = 评审后的最终版本 | P0 |
| F-9-2 | 用例质量自动评估 | 建立 LLM-as-Judge 自动评估器：从字段规范性、步骤可执行性、预期结果明确性、业务规则符合度、覆盖完整度等维度对生成用例自动打分；评估标准以人工评审数据持续校准（评估器与人工判断的一致率作为其自身质量指标） | P1 |
| F-9-3 | Prompt 自动优化 | 基于失败/高修改率案例，系统定期自动生成 Prompt 改进候选（如补充约束、增加反例），在评估集上自动回归测试，优于当前版本才允许发布；Prompt 版本化管理，支持一键回滚 | P1 |
| F-9-4 | 坏案例归因分析 | 对被删除/大改的用例自动归因：需求解析错误 / 知识检索未命中 / 知识过期 / Prompt 约束不足 / 模型能力不足，归因结果分发到对应模块的优化队列（如检索未命中→知识库补充建议） | P1 |
| F-9-5 | 逃逸缺陷自动学习 | 对接缺陷管理系统（禅道/Jira），迭代结束后自动分析逃逸缺陷：反推"本应生成但未生成的用例"，自动转化为知识库规则条目草稿与 Prompt 检查项候选，经人工确认后生效 | P2 |
| F-9-6 | 模型持续微调 | 当学习语料积累到阈值（建议 ≥ 3000 条高质量样本）后，支持对内部私有化模型进行 SFT/LoRA 微调（人工终稿作为标注答案），微调版本经评估集验证优于基线后灰度上线；采购 token 的商用模型不参与微调，仅受益于 Prompt 优化 | P2 |
| F-9-7 | A/B 实验框架 | 支持 Prompt 版本、模型版本、配额策略的 A/B 对比实验（按任务随机分流），以采纳率/修改率为决策指标，保证每次"进化"有数据支撑而非凭感觉 | P2 |
| F-9-8 | 学习效果防退化 | 维护固定的黄金评估集（人工精标的需求→用例样本），任何 Prompt/模型变更上线前必须通过黄金集回归，防止优化某类问题时引入新的退化 | P1 |
| F-9-9 | 学习过程可审计 | 所有自动优化行为（Prompt 变更、归因结论、微调上线）留痕可查，重大变更需管理员审批，系统不允许完全无人监督的自我修改 | P0 |

## 5. 核心流程

### 5.1 主流程

```
用户上传需求文件(PDF/Word/图片) + 选择用例模板 + 选择模型
        │
        ▼ [主控 Agent 建单调度]
需求分析 Agent：格式识别 → 文本/结构提取(图片走多模态/OCR) → 测试点拆解
        │    ↕ 知识管家 Agent：检索测试用例库比对覆盖度查漏（拆解阶段）
        ▼
(可选) 解析与拆解结果预览，用户确认
        │
        ▼
知识管家 Agent 检索编排：
  检索 玩法/业务规则库 + 需求文档库 → 注入用例生成 Agent
  冲突仲裁(F-7-12) / 配额分配 5:3:2 与让渡 / 记录知识快照(F-7-13)
  同时检索记忆系统（用户偏好+项目记忆，独立配额 ≤5%-10%）
        │        → 引用的知识片段与记忆对用户可见
        ▼
用例生成 Agent（大需求按模块并行多实例）：按模板生成详细用例
        │
        ▼
评审 Agent（Critic，强制执行）：字段合规/步骤-预期对应/编号连续/
  覆盖度比对/明显遗漏检查 → 不合格带问题打回定点修正（≤3轮回环）
        │
        ▼
输出模块：生成 XMind + Excel/CSV → 用户下载
        │
        ▼
(可选) 主控 Agent 多轮对话修订 → 路由至生成/评审 Agent → 增量更新重导出
        │
        ▼
评审闭环（度量与学习的数据源，不可缺省）：
  路径A 在线评审：逐条采纳/修改/删除留痕（推荐）
  路径B 离线评审：下载 → 外部评审 → 回传评审终稿 → 系统自动 diff 生成留痕
        │
        ▼ [学习 Agent 离线异步]
任务结束：留痕 → 学习语料(F-9-1) / 效果度量(第11章)
         会话提炼 → 偏好/纠正/项目事实写入长期记忆(F-8-5)
         优质用例 → 可选回存测试用例库(F-7-9，带来源标记)
```

### 5.2 异常流程

| 异常场景 | 处理策略 |
|---|---|
| 文件格式不支持/损坏 | 前置校验拦截，提示支持的格式清单 |
| OCR/解析结果为空 | 提示用户文件可能为扫描件质量过低，建议更换文件或粘贴文本 |
| 模型调用超时/失败 | 自动重试 N 次 → 降级备用模型 → 仍失败则任务标记失败并保留上下文供重跑 |
| 生成结果不符合模板 | 自动携带校验错误信息重新生成，最多 3 次，仍失败则输出并标注不合规项 |
| 需求超长 | 自动分片 + 分段生成 + 合并去重 |
| 知识库检索无命中 | 正常降级为无知识注入生成，并在结果中提示"未检索到相关业务知识" |
| 检索命中过多超出上下文 | 按相似度截断 Top-K + 片段压缩摘要后注入 |
| 多文件上传部分文件解析失败 | 不阻塞整体任务：成功文件继续，失败文件明确列出并提示影响范围，用户可选补传后增量重解析 |
| 知识与需求内容冲突 | 以当前需求为准，标注冲突点并提示为重点测试对象（F-7-12），冲突记录反馈知识库管理员 |
| 用户指出记忆错误（"你记错了"） | 立即修正/删除对应记忆条目并确认，被纠正的记忆不再参与本次及后续注入；纠正行为本身作为高置信记忆写入 |
| 生成-评审回环达到上限仍不合格 | 3 轮回环后强制出稿，未解决项在结果中显式标注"评审未通过项"供人工重点关注，同时记录为坏案例进入归因队列（F-9-4） |
| 并行生成实例部分失败 | 成功模块正常产出，失败模块单独重试；最终汇总时标注缺失模块，不阻塞整体交付 |

## 8. 验收标准（关键项）

1. 支持至少 3 家不同厂商模型的接入与任务级切换，切换后功能表现一致。
2. PDF、Word、图片三类输入均可正确解析并生成用例；图片输入可正确识别界面元素并生成对应 UI 用例。
3. 上传自定义模板后，导出的 Excel 字段与模板 100% 一致，无缺失字段。
4. 同一任务导出的 XMind 与 Excel 用例内容一致；XMind 可被 XMind 客户端正常打开。
5. 多轮对话修订后，可增量更新用例并重新导出。
6. 模型调用失败场景下重试与降级机制生效，任务不产生脏数据。
7. 三大知识库均可验证效果：启用**玩法/业务规则库**后用例体现业务规则（如数值上限、道具消耗逻辑、流程分支）；启用**需求文档库**后能识别新旧功能关联并补充回归用例；启用**测试用例库**后生成用例的风格粒度与历史用例一致；结果中均可查看本次引用的知识片段。
8. 知识空间权限隔离生效：无权限用户创建任务时不可选择、不可检索到该知识空间内容。
9. 记忆功能可验证：同一用户在新会话中创建同项目任务，Agent 能自动应用其历史偏好（如模板选择、用例粒度）与项目上下文，无需重复说明；用户可在记忆管理页查看、编辑、删除记忆条目。
10. 修改习惯学习生效：对同一用户连续多次做出相同类型修改后（如补充某类字段），后续生成结果不再出现该类问题。
11. 自我学习闭环可验证：评审留痕能自动生成标准化学习语料；Prompt 优化候选须通过黄金评估集回归才可发布且支持回滚；所有自动优化行为留痕可审计。
12. 评审闭环完整性：在线评审与离线终稿回传（diff 留痕）两条路径均可产出等效评审数据；仅走"下载-离线评审"工作流的任务同样能进入度量统计与学习语料。
13. 知识冲突仲裁生效：当知识库内容与需求矛盾时，生成结果以需求为准且明确标注冲突点为重点测试对象；任务详情可查看本次注入知识的快照清单。
14. 多 Agent 协作可验证：生成与评审由独立 Agent 承担（Prompt 独立、可配置不同模型）；评审不合格项能带具体问题定点打回修正（≤3 轮）；任务详情可查看完整 Agent 调用链路；大需求可按模块并行生成且汇总后编号连续、无模块遗漏。

## 10. 风险与待确认事项

| 编号 | 风险/待确认项 | 说明 |
|---|---|---|
| R1 | 用例模板样例 | 需提供贵团队实际用例模板文件，用于字段识别方案设计 |
| R2 | XMind 目标版本 | 需确认团队使用的 XMind 版本（2020+ 的 .xmind 与旧版 XMind 8 格式不兼容） |
| R3 | 模型数据合规（已确认方案） | 模型来源两种方式并存：**公司内部自行搭建私有化大模型**（数据不出内网），或**直接采购商用大模型 token**（走官方 API）。LLM 适配层须同时支持两类接入（均走 OpenAI 兼容协议为佳）；采购商用 token 时需求文档会经外部 API 传输，涉密项目须由管理员限制只能使用内部模型 |
| R4 | 生成质量预期 | LLM 生成用例为"高质量初稿"，仍需人工评审，需在团队流程中明确定位 |
| R5 | 图片需求复杂度 | 复杂流程图/时序图的理解准确率依赖多模态模型能力，需 POC 验证 |
| R6 | 知识库冷启动（已确认方案） | 知识库确定为三大分类：**①测试用例库**（历史用例导入）、**②需求文档库**（以往 PRD）、**③玩法/业务规则库**（游戏玩法说明与规则，或业务说明与业务流程），首批知识由需求方提供。系统需针对三类知识源分别设计入库解析与切片策略 |
| R7 | 知识时效性 | 业务规则变更后旧知识可能误导生成，需明确知识更新与失效标记的维护机制 |
| R8 | 检索质量 | 中文业务文档的切片与 Embedding 效果需 POC 对比（bge/m3e/商用模型），检索准确率直接影响用例业务相关性 |
| R9 | 私有化模型能力边界（部分已确认） | ①多模态（Vision）能力：**已确认具备**——内部搭建的模型将具备多模态能力，或直接采购商用大模型 token，图片类需求（原型图/截图）走多模态直接理解，OCR 仅作兜底；②知识注入上下文分配：**已确认按 5:3:2**（测试用例库:需求文档库:玩法与业务规则库）；③生成质量仍需 POC 基线对比（内部模型 vs 商用模型），据此决定 Prompt 调优方向 |
| R10 | 自我学习冷启动与数据质量 | 自我学习依赖评审留痕数据的量与质：若试点期用户评审不认真（直接全采纳/全删除），语料会污染学习方向。需在试点期 SOP 中明确评审要求，并对语料做质量过滤（如剔除无差异全采纳样本中的低价值部分） |
| R11 | 自动优化失控风险 | Prompt/模型的自动优化若缺乏约束可能引入退化或不可预期行为。已通过三重防护约束：黄金评估集强制回归（F-9-8）、重大变更管理员审批（F-9-9）、版本化可回滚（F-9-3），落地时不可裁剪这三项 |

## 11. 落地实施方案与效果度量

> 本章目的：确保项目不停留在"能生成用例"，而是真正融入测试团队日常流程并可量化验证价值。AI 用例生成类项目落地失败的主因通常不是技术，而是缺少人机协同定位、效果度量与渐进推广策略。

### 11.1 人机协同定位

| 原则 | 说明 |
|---|---|
| AI 产出定位为"高质量初稿" | 生成用例必须经人工评审后才进入正式用例库/测试执行，Agent 不替代测试人员的评审职责 |
| 评审动作留痕 | 评审时对每条用例的操作（采纳/修改后采纳/删除）系统记录，作为效果度量与 Prompt 优化的数据来源 |
| 修改反馈闭环 | 人工修改的差异（AI 原稿 vs 评审终稿）沉淀为优化素材：高频修改模式反哺 Prompt 与知识库 |

### 11.2 核心度量指标

| 指标 | 定义 | 目标参考值 |
|---|---|---|
| 用例采纳率 | 直接采纳 + 小改采纳的用例数 / 生成总数 | 上线 3 个月 ≥ 70% |
| 人工修改率 | 需要修改的字段数 / 总字段数 | 持续下降趋势 |
| 编写提效比 | (人工编写工时 - AI 辅助后工时) / 人工编写工时（数据来源：试点期人工抽样对比统计，推广后按需求规模抽查） | ≥ 60% |
| 覆盖度增益 | AI 生成用例中人工评审认定"人工容易遗漏"的用例占比 | 持续跟踪 |
| 逃逸缺陷回溯 | 线上/测试后期发现的缺陷中，本可由用例覆盖但 AI 与人工均未生成的场景数 | 逐迭代下降 |
| 知识库命中率 | 生成任务中检索到有效知识片段的任务占比 | ≥ 80% |

### 11.3 分阶段推广策略

| 阶段 | 范围 | 目标与退出标准 |
|---|---|---|
| 试点期（4-6 周） | 选择 1 个游戏项目 + 1 个非游戏业务线，各指定 2-3 名种子用户 | 采纳率 ≥ 50%，收集高频修改模式，完成 Prompt 与知识库首轮调优 |
| 扩大期（4-8 周） | 覆盖试点业务线全体测试人员 | 采纳率 ≥ 70%，提效比 ≥ 50%，形成标准使用 SOP |
| 全面推广 | 全测试团队，纳入日常测试流程（需求评审后即触发用例生成） | 指标看板常态化运营，知识库进入自增长状态 |

### 11.4 持续优化机制（人工节奏 + 自动学习）

1. **实时自动**：评审留痕自动加工为学习语料（F-9-1）；坏案例自动归因分发（F-9-4）。
2. **周度**：查看采纳率/修改率看板，收集用户反馈（系统内置"一键反馈本条用例问题"入口）。
3. **双周**：审批系统自动生成的 Prompt 优化候选（F-9-3，黄金集回归通过后发布）；结合归因结果人工补充优化。
4. **月度**：知识库质量巡检（过期规则标记失效、低命中知识清理），评估是否调整 5:3:2 注入配额；A/B 实验结论评审。
5. **迭代级**：逃逸缺陷自动学习结果确认（F-9-5），漏测场景转化为知识库规则与 Prompt 检查项。
6. **阶段性**：学习语料达到阈值后启动私有化模型微调（F-9-6），灰度验证后上线。

> 数据飞轮：使用越多 → 评审留痕越多 → 语料/归因越丰富 → Prompt与模型越优 → 采纳率越高 → 使用意愿越强。
>
> **飞轮的前提**：评审数据必须回得来。因此在线评审（F-6-6）与离线终稿回传（F-6-8）双通道为闭环必选能力，任何一条落地方案裁剪都会导致度量、记忆学习、自我学习三个体系同时失效。
